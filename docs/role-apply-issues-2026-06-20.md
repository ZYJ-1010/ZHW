# 角色申请问题记录 - 2026-06-20

本文记录“首页-其他”角色申请流程当前发现的待确认问题。此文档只做问题记录，不代表最终产品方案。

## 1. 申请入口 / 申请动作重复

- 模块：`首页 / 角色申请`
- 涉及页面：
  - `pages/home-other/index`
  - `pages/home/player/index`
  - `pages/role/apply/index`
  - `pages/role/status/index`
- 涉及接口：
  - `POST /api/app/role-applications`
  - `GET /api/app/role-applications/my`
  - `GET /api/app/roles/my`
- 当前情况：
  - `pages/home-other/index` 新页面中有申请领路人浏览页和申请领路人内页提交动作。
  - 项目原有 `pages/role/apply/index` 也承载角色申请入口。
  - 当前临时实现为：`pages/home-other/index` 提交 `roleType: guide` 后 toast 提示并回玩家首页，`pages/home/player/index` 根据 pending 状态展示审核中。
- 待确认问题：
  - 玩家从首页点击申请角色时，正式入口到底进入 `pages/home-other/index` 里的申请页，还是进入原有 `pages/role/apply/index`？
  - 是否需要同时保留两个申请入口？
  - 若用户重复点击提交申请，前端和后端分别如何处理？
  - 行家申请和领路人申请是否走同一个入口，只靠 `roleType` 区分？
- 来源：用户 2026-06-20 反馈“这里有两个申请这是有问题的”。
- 状态：待业主确认。

## 2. 行家计划书 / 领路计划书填写规则不明确

- 模块：`首页 / 角色申请`
- 涉及页面 / 文档：
  - `pages/home-other/index`
  - `pages/home/index`
  - `pages/role/status/index`
  - `docs/api-additions.md`
- 涉及接口：
  - `POST /api/app/role-applications`
  - `GET /api/app/role-applications/my`
  - 如后续需要动态配置申请表单，还需确认是否新增配置接口。
- 当前情况：
  - `pages/home-other/index` 的领路人内页目前参考申请行家内页样式制作。
  - 当前领路人内页包含：领路计划书、资质证明、3 组业务定价 / 成本。
  - `pages/home/index` 中已有行家计划书相关展示。
  - `pages/role/status/index` 中已有领路计划书审核状态和驳回建议文案。
- 待确认问题：
  - 行家计划书具体需要填写哪些字段？
  - 领路计划书具体需要填写哪些字段？
  - 行家计划书和领路计划书是否共用同一套表单结构？
  - 领路计划书是否也需要 3 组业务定价 / 服务成本？
  - 资质证明要上传哪些材料，是否行家和领路人一致？
  - 提交接口字段如何组织，是否需要后端返回表单配置和校验规则？
- 计划书详细页当前草案：
  - 行家计划书详细页：
    - 基础信息：技能领域、技能标签、从业年限。
    - 计划说明：个人简介 / 行家申请说明，需描述专业背景、服务风格、擅长领域、可提供的服务内容。
    - 资质证明：作品集、证书、案例、资质材料等上传内容，支持 JPG、PNG、PDF，最多 5 份。
    - 业务配置：3 组业务，每组包含业务名称、服务定价（元 / 小时）、服务成本。
    - 提交动作：提交行家申请，提交后进入审核流程。
  - 领路计划书详细页：
    - 基础信息：所在城市、可推荐人群、常用联系方式。
    - 计划说明：领路计划书，需描述带队风格、过往战绩、人脉 / 资源、组局规划，以及如何帮助玩家完成组局。
    - 资质证明：作品集、组局记录、案例、资源证明或其他凭证，支持 JPG、PNG、PDF，最多 5 份。
    - 业务配置：当前临时参考行家内页，也包含 3 组业务名称、服务定价（元 / 小时）、服务成本；是否保留需确认。
    - 提交动作：提交领路人申请，提交后 toast 提示“申请已提交，请耐心等待审核结果”，再返回首页，由首页根据后台申请状态展示审核中。
- 需要后端 / 业主进一步明确：
  - “计划书”是否就是接口里的 `intro`，还是需要独立字段，如 `planContent`、`expertPlan`、`guidePlan`。
  - 行家和领路人的计划书字段是否共用同一套字段结构，还是各自配置。
  - 3 组业务定价 / 服务成本是否两个角色都需要；若需要，后端字段名、金额类型和校验规则是什么。
  - 资质证明是否先上传文件再提交 `certFileIds`，还是申请接口可直接接收文件信息。
  - 审核驳回时，后台是否按字段返回问题和改进建议，用于前端按内容自适应展示。
- 来源：用户 2026-06-20 反馈“领路计划书也是不清楚怎么填和行家的计划书，需要业主确认”。
- 状态：待业主确认。

## 3. 申请领路人是否需要独立内页不明确

- 模块：`首页 / 角色申请`
- 涉及页面 / 文档：
  - `pages/home-other/index`
  - `pages/home/index`
  - `pages/role/apply/index`
  - `docs/api-additions.md`
  - `E:\项目\03周总\00.文档\PRD.md`
  - `E:\项目\03周总\00.文档\接口、数据库初稿.md`
  - `E:\项目\03周总\00.文档\功能清单.md`
- 当前文档口径：
  - PRD 中行家定义为“服务交付者”，主要能力是创建局、审核入局申请、组织局内服务、反馈局进度、参与服务确认、获得评价和分润记录。
  - PRD 中领路人定义为“资源撮合者”，主要能力是邀请玩家入局、跟进撮合记录、查看自己撮合的局和用户、参与评价反馈、获得撮合和分润记录。
  - PRD 明确“领路人不等同行家”，领路人不能越权修改局核心规则，领路人邀约也不能绕过发起人或行家的终审。
  - PRD 仅明确“用户可申请行家或领路人”“行家和领路人均需后台审核”，并明确领路人需要满足平台条件和完成付费后才可进入审核或开通流程。
  - 功能清单中“领路人申请”的小程序侧写的是“申请表单”，未明确拆分为“操作页 + 内页”。
  - 接口初稿中存在通用角色申请接口 `POST /api/app/roles/applications`，也存在领路人专项接口 `POST /api/app/guides/apply`，但未明确对应页面层级。
- 当前页面情况：
  - `pages/home-other/index` 已按用户要求临时制作“申请领路人操作页 + 申请领路人内页”，其中内页参考申请行家内页样式。
  - 该实现目前属于前端静态/编译走查页面，不代表最终产品已经确认必须有领路人独立内页。
- 待确认问题：
  - 申请领路人是否和申请行家一样，需要“操作页 + 详情填写内页”两级页面？
  - 由于行家偏服务交付、领路人偏资源撮合，领路人内页字段是否应区别于行家内页，例如突出资源标签、可推荐人群、关系网络、撮合能力，而不是完全沿用行家技能 / 服务表单？
  - 领路人内页是否应使用专项接口 `POST /api/app/guides/apply`，还是复用通用角色申请接口并传 `roleType: guide`？
  - 领路人双门槛流程中，条件未满足、未付费、待审核、已开通分别应该进入哪个页面？
  - 若没有独立内页，领路计划书、资质证明、业务定价 / 成本应放在哪个页面提交？
- 来源：用户 2026-06-21 反馈“申请领路人没有内页吗？文档里有怎么提？领路人和行家区别是什么？”
- 状态：待业主确认。

## 4. 多角色用户是否需要先切换角色再使用对应功能

- 模块：`首页 / 角色权限 / 角色切换`
- 涉及页面 / 文档：
  - `pages/home/player/index`
  - `pages/home/expert/index`
  - `pages/home/guide/index`
  - `components/role-dashboard-home/index`
  - `docs/api-additions.md`
  - `E:\项目\03周总\00.文档\PRD.md`
  - `E:\项目\03周总\00.文档\接口、数据库初稿.md`
  - `E:\项目\03周总\00.文档\功能清单.md`
- 当前文档口径：
  - PRD 明确“一个用户可以同时拥有多个角色”，且前端按角色展示入口，后端按角色校验接口权限。
  - 功能清单中有“一人多角色 / 角色入口切换 / 权限判定”，验收口径为同一用户可同时拥有玩家、行家、领路人。
  - 接口初稿中 `GET /api/app/users/me` 返回用户角色，`GET /api/app/roles/my` 返回已开通角色及权限。
  - 数据库 `users.default_role` 字段表示当前默认角色，但 `CurrentUserDTO` 中是否正式返回 `defaultRole/default_role` 仍待确认。
  - `docs/api-additions.md` 已记录后续真实入口不应由前端固定猜测进入哪个角色首页，应由后台返回当前默认角色或已开通角色后决定进入玩家、行家或领路人首页。
- 当前问题：
  - 如果一个用户同时拥有玩家、行家、领路人三种角色，是否必须先选择 / 切换当前角色，再进入该角色的首页和功能。
  - 用户切换到某个角色后，是否所有操作都应带上当前角色上下文，例如玩家操作、行家服务操作、领路人撮合操作分别隔离。
  - 如果用户点击未开通或审核中的角色，应该展示无权限页、申请页、审核进度页，还是仍停留在当前角色首页。
  - 是否需要后端提供“保存当前角色 / 切换角色”的接口；现有文档只看到查询角色与默认角色字段，未看到明确的切换保存接口。
- 待确认问题：
  - 用户进入小程序时，默认角色以后台 `defaultRole/default_role` 为准，还是以前端本地最近选择角色为准。
  - 是否新增接口保存用户当前选择角色，例如 `PUT /api/app/users/me/default-role` 或 `POST /api/app/roles/switch`。
  - 首页角色切换时，是只前端切换并调用 `GET /api/app/home?roleType=...`，还是必须先调用后端切换接口。
  - 后端业务接口是否都需要接收或识别当前角色上下文，避免用户未切换角色时执行其他角色功能。
  - 多角色用户在同一页面里是否允许跨角色操作，还是必须进入对应角色首页后才能操作对应功能。
- 来源：用户 2026-06-21 反馈“既然用户可以有 3 种角色，是不是用户切换角色才能进行相应角色的功能？”
- 状态：待业主确认。
