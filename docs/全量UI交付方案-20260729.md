## 1. 先确认“全量 UI”指什么

建议让甲方在以下三种口径中确认：

| 口径 | 内容 | 当前能否直接提供 |
| --- | --- | --- |
| 代码现状 UI | 当前小程序和后台运行后的全部页面截图 | 可以，但需要固定版本、账号和测试数据 |
| 产品设计 UI | 可编辑设计源、组件库、标注、切图、交互原型 | 仓库没有 Figma/Sketch/XD 源文件；需从原设计方或墨刀导出 |
| 验收全量 UI | 页面、弹窗、加载、空态、错误态、权限态、业务状态全覆盖 | 可以制作，但不能只按路由截图，需要状态数据和账号配合 |

推荐对甲方采用第三种口径，并同时附上设计源可用情况说明。

## 4. 页面清单字段

每个页面或状态至少记录：

| 字段 | 示例 |
| --- | --- |
| 编号 | `MP-GAME-012` |
| 端 | 小程序/PC 后台 |
| 模块和页面名 | 组局-入局申请 |
| 角色 | 玩家/行家/领路人/管理员 |
| 代码路由 | `pages/game/apply/index` |
| 原型画布 | 墨刀画布 ID |
| 状态 | 默认/加载/空/错误/成功/禁用 |
| 入口 | 从哪个页面、点击什么进入 |
| 截图文件 | `MP-GAME-012-default.png` |
| 实现状态 | 已实现/预留/未注册/待确认 |
| 差异说明 | 与原型或需求的差异 |

当前 CSV 已提供页面和源码基础清单；正式交付时再补角色、入口、状态、截图名和验收结果。

## 5. 必须覆盖的状态

### 小程序通用状态

- 未登录、预认证、已登录、Token 失效；
- 加载、空数据、接口失败、无网络、重试；
- 无权限、未实名、角色审核中/通过/驳回；
- 表单默认、校验失败、提交中、提交成功；
- 列表默认、筛选、无结果、分页结束；
- 弹窗、抽屉、选择器、确认和取消。

### 关键业务状态

- 局：草稿、待审核、招募、满员、进行中、待确认、待评价、完成、取消；
- 入局：未申请、待审核、通过、拒绝、取消；
- 邀约：待响应、接受、拒绝、失效；
- IM：无消息、有消息、文件、发送失败、只读；
- 评价：待评价、已评价、低分、再玩一局；
- 信用/积分/订单：正常、受限、不足、取消、完成；
- 举报/反馈：待处理、处理中、已完成、撤回；
- 后台：有权限、无权限、空列表、详情、审核弹窗、操作成功/失败。

## 6. 截图标准

| 项目 | 建议标准 |
| --- | --- |
| 小程序基准 | 与原型一致使用 375×812 逻辑尺寸；导出高清 PNG |
| 后台基准 | 1440×900，必要时补 1920×1080 |
| 数据 | 使用固定验收账号和脱敏数据，不使用随机数据 |
| 文件格式 | PNG；长页保留完整长截图和首屏截图 |
| 命名 | `端-模块-序号-页面-状态.png` |
| 版本 | 每批截图写 Git 提交号、接口环境和生成日期 |
| 隐私 | 手机、身份证、微信标识、聊天证据必须脱敏 |

## 7. 本项目当前需要先处理的事项

1. 固定一个 Git 提交号；当前工作区有大量未提交改动，不能直接作为正式 UI 基线。
2. 明确截图环境：本地、测试或生产；不建议混用。
3. 准备玩家、行家、领路人和不同权限管理员账号。
4. 准备覆盖局、申请、邀约、评价、信用、举报等状态的固定数据。
5. 决定 8 个未注册页面是否纳入一期交付。
6. 补齐或确认 6 个地图玩法页面的交付边界。
7. 明确墨刀只读链接能否对外，以及甲方是否要求可编辑源文件。
8. 根据现有视觉差距清单逐页验收，不能把“路由存在”直接等同于“UI 已还原”。

## 8. 推荐交付流程

1. **范围确认**：甲方签字确认页面和状态清单。
2. **版本冻结**：记录 Git 提交号、测试环境、账号和数据版本。
3. **自动遍历**：按页面清单逐页打开并截图。
4. **状态补拍**：补充无法通过普通路由覆盖的弹窗和业务状态。
5. **三方映射**：原型画布、代码路由、截图文件一一对应。
6. **差异确认**：预留、缺图、未注册和未实现项单独列出。
7. **压缩交付**：生成校验值，保留内部备份和甲方签收记录。

## 9. 可直接回复甲方的话术

> 可以提供全量 UI。为避免只交一批无法核对的截图，我们会按“小程序页面、PC 管理后台、弹窗与业务状态”整理全量清单，并同时提供高清截图、页面路由、原型对应关系、设计规范和差异说明。当前仓库有 112 个已注册小程序页面、18 个后台一级视图和 105 个原型画布。请先确认需要的是当前代码截图、可编辑设计源文件，还是包含加载/空态/异常/权限状态的验收全量 UI；三种交付范围和工期不同。

## 10. 结论

当前最稳妥的交付不是“直接打包所有图片”，而是先用本项目的 UI CSV 作为范围底稿，让甲方确认页面和状态，再按固定版本生成截图包。若甲方要求可编辑设计源文件，需要另行取得墨刀/Figma 原始文件授权；仅凭现有代码和 PT 归档不能反向承诺完整设计源。
