## 1. 文档目标

本文用于明确“真好玩小程序”第一期产品需求，统一产品范围、角色权限、核心流程、功能细节、后台能力、接口数据边界、验收标准和不纳入一期的内容。

第一期不是展示型小程序，也不是普通活动报名工具，而是以“局”为核心的服务交易闭环系统。第一期交付必须做到：用户只能通过邀请海报、邀请二维码、邀请链接三种形式进入小程序，每次邀请都携带唯一邀请码；玩家可作为基础用户参与流程；行家和领路人必须完成实名认证与角色审核后才能使用对应能力；用户可创建和参与局、进入局内 IM 沟通、完成服务确认和评价、沉淀成长信用与收益记录，后台能审核、配置、查询、处理异常并完整留痕。

---

## 2. 产品定位

“真好玩”是一个连接人与服务的个性化组局平台。平台通过唯一邀请制、行家 / 领路人实名制、角色审核、局内沟通、评价信用、分润记录和后台管控，把非标服务从“靠私下沟通”变成“可创建、可审核、可参与、可追踪、可评价、可结算”的线上流程。

平台核心对象是“局”。一个局可以理解为一次服务协作、一次线下体验、一次资源撮合或一次任务交付的最小业务单元。所有用户、角色、IM、评价、分润、投诉、足迹和后台管理都围绕局展开。

## 3. 一期目标

### 3.1 核心目标

第一期目标是完成可真实运行的核心业务闭环：

```text
邀请注册
-> 微信登录
-> 玩家基础使用 / 行家和领路人实名认证
-> 行家和领路人角色申请与审核
-> 创建局 / 浏览局
-> 后台自动审核或人工复核局
-> 玩家申请入局 / 领路人邀约
-> 发起人或行家审核入局
-> 满 5 人后开始或 8 人满员自动成团
-> 自动创建局内 IM
-> 局内沟通和文件传输
-> 行家反馈局进度
-> 服务确认
-> 评价、再玩一局意向、成长信用
-> 分润记录和收益记录
-> 举报申诉和后台处理
-> 后台数据追踪、日志、报表导出
```

### 3.2 一期完成标准

1. 小程序端能完成核心用户流程，不只是页面展示。
2. PC 后台能审核、配置、查询、处理异常。
3. 所有关键业务对象有状态机和日志。
4. 前后端字段、接口、数据库能按《接口、数据库初稿.md》对齐。
5. 一期虽不正式做 AI 推荐、真实支付分账、高级地图玩法，但必须沉淀二期所需数据。

## 5. 用户角色

### 5.1 玩家

玩家是平台的基础用户，可以通过唯一邀请进入、微信登录、浏览局、申请入局、接收领路人邀约、进入局内 IM、确认服务、评价、查看个人成长和收益记录；玩家不强制实名认证。

玩家作为某个局的发起人时，在该局范围内可以拥有部分管理权限，例如查看申请、决定是否开始、服务确认等。

### 5.2 行家

行家是服务交付者，需要提交申请并通过后台审核。行家可以创建局、审核入局申请、组织局内服务、反馈局进度、参与服务确认、获得评价和分润记录。

行家不得绕过后台审核直接拥有行家能力。行家在审核入局时必须由后端再次校验人数和局状态。

### 5.3 领路人

领路人是资源撮合者，需要满足平台条件并完成付费后，才可进入审核或开通流程。领路人可以邀请玩家入局、跟进撮合记录、查看自己撮合的局和用户、参与评价反馈、获得撮合和分润记录。

领路人不等同行家，不能越权修改局核心规则。领路人邀约不能绕过发起人或行家的终审。

### 5.4 管理员

后台管理员分级管理，至少包括：

| 角色 | 权限范围 |
| --- | --- |
| 超级管理员 | 全部权限、管理员管理、高风险配置、完整操作日志查看 |
| 运营管理 | 组局审核、内容审核、局状态管理、IM 争议协助 |
| 用户管理 | 用户资料、实名状态、角色状态、邀请绑定关系 |
| 财务管理 | 分润比例、分润计算、结算记录、二期支付预留数据 |
| 客户管理 | 客户资料、服务跟进、投诉申诉协助 |
| 数据分析员 | 用户足迹、漏斗留存、数据看板、报表导出，只读为主 |
| 组局管理 | 组局审核、局列表、局状态、订单查看、后台创建局 |

## 7. 功能需求

### 7.1 邀请注册与账号

#### 需求

1. 用户必须通过邀请海报、邀请二维码、邀请链接三种形式之一进入小程序。
2. 每个邀请入口都必须携带唯一邀请码，小程序不可被检索，也不提供无码进入。
3. 用户通过邀请进入后，系统自动把邀请码写入邀请码输入框。
4. 进入时后端先校验邀请码是否有效，并判断该邀请码是否已绑定唯一微信身份。
5. 如果邀请码未绑定微信身份，进入注册界面，用户完成微信登录后绑定邀请码和微信身份。
6. 如果邀请码已绑定唯一微信身份，进入登录界面，不再走注册界面。
7. 邀请关系默认永久绑定，普通用户不可自行修改。
8. 后台可以创建、修改、禁用邀请海报、二维码、链接对应的邀请码配置。
9. 后台可以管理邀请绑定关系，但必须有权限控制和操作日志。

#### 验收

1. 无有效邀请码时，用户不能进入小程序。
2. 通过海报、二维码、链接进入时，邀请码能自动填入输入框。
3. 未绑定微信的邀请码展示注册界面，已绑定唯一微信的邀请码展示登录界面。
4. 用户注册后，后台可查邀请人、被邀请人、绑定微信、绑定时间和状态。
5. 后台修改邀请关系时，操作日志记录操作人、时间、前后变化。

### 7.2 实名认证

#### 需求

1. 行家和领路人可提交姓名、手机号、身份证号和实名材料。
2. 实名资料进入后台自动审核或人工复核状态。
3. 后台可审核通过或驳回。
4. 驳回必须填写原因。
5. 玩家不强制实名，但未实名的行家和领路人不能进入对应能力和收益流程。

#### 验收

1. 用户端可提交和查看审核状态。
2. 后台可查看实名资料并审核。
3. 未实名的行家或领路人访问对应核心接口时被后端拦截。

### 7.3 角色申请与权限

#### 需求

1. 用户默认是玩家。
2. 用户可申请行家或领路人。
3. 行家和领路人均需后台审核。
4. 一个用户可以同时拥有多个角色。
5. 前端按角色展示入口，后端按角色校验接口权限。
6. 玩家不要求实名认证；行家和领路人必须实名认证后才可开通。
7. 管理员权限分级，普通管理员不能操作高风险配置。

#### 验收

1. 未审核用户不能使用行家或领路人功能。
2. 后端接口不能只依赖前端隐藏按钮。
3. 后台可查看申请记录、审核记录、驳回原因。

### 7.4 领路人双门槛

#### 需求

1. 申请成为领路人需要满足平台条件。
2. 申请成为领路人需要完成付费。
3. 只付费但条件未满足，不能开通。
4. 条件满足但未付费，不能开通。
5. 条件和付费都满足后，进入后台审核或开通流程。
6. 一期可先保留付费订单和状态，不接真实支付时由后台登记。

#### 验收

1. 用户端可查看条件达成情况。
2. 后台可配置领路人申请条件。
3. 不满足双门槛时，接口不能返回已开通状态。

### 7.5 创建局

#### 需求

1. 玩家或行家可创建局。
2. 创建局字段包括标题、类型、主题、介绍、服务内容、人数、地点、经纬度、时间、标签、封面、发起人、行家、领路人。
3. 每局参与人数必须在 5-8 人范围内。
4. 每人每日最多创建 3 局。
5. 小程序端一期只开放免费局。
6. 后台可以创建任意类型的局，包括免费局、收费局、公益局、AA 局、众筹局、押金局、条件局。
7. 一期条件局只允许后台创建。
8. 用户端创建后需进入后台审核，不应直接展示。

#### 验收

1. 第 4 次创建局被后端拦截。
2. 人数小于 5 或大于 8 时无法提交。
3. 未实名的行家不能创建局；玩家作为发起人创建局不强制实名。
4. 后台可查看并审核局。

### 7.6 局审核

#### 需求

1. 后台审核主题、介绍、服务内容、地点、行家资质、领路人身份、违规风险。
2. 审核通过后进入招募中。
3. 审核驳回后返回修改，并记录驳回原因。
4. 审核记录必须留存。

#### 验收

1. 未审核通过的局不出现在公开列表。
2. 后台可查看审核历史。
3. 审核动作写入操作日志。

### 7.7 浏览局、同城与附近

#### 需求

1. 用户可浏览审核通过且状态正常的局。
2. 支持局列表和局详情。
3. 支持同城筛选。
4. 支持附近局推荐。
5. 支持距离排序。
6. 支持距离角标，例如 `300m`、`1.2km`。
7. 微信定位精度控制在 300m，超过时提示或兜底。
8. 用户未授权微信定位时，可手动选择位置。
9. 用户可以选择尚未到达但准备前往的位置查看附近局。

#### 验收

1. 定位误差超过 300m 时有提示。
2. 手动定位可用于附近局列表。
3. 同城筛选、距离排序、距离角标可用。
4. 后台可查看局地点信息。

### 7.8 入局申请与领路人邀约

#### 需求

1. 玩家可申请入局。
2. 领路人可邀请玩家入局。
3. 玩家处理邀约后进入申请或拒绝流程。
4. 申请需要发起人或主行家审核。
5. 审核通过时后端再次校验局状态、人数和重复申请。
6. 满员、已开始、已取消、已结束的局不能申请。
7. 领路人邀约不能绕过发起人或主行家终审。
8. 玩家邀请一名行家后，该行家可作为主行家；其他行家可由主行家继续邀请加入协作。

#### 验收

1. 重复申请被拦截。
2. 满员后不能继续通过申请。
3. 领路人邀约记录、玩家响应、最终是否入局可追踪。
4. 主行家和协同行家的关系、进度归属可追踪。

### 7.9 达到 5 人后开始与状态锁定

#### 需求

1. 如果人数未达到设定人数，不允许手动开始。
2. 达到 5 人后，发起人或主行家可以开始。
3. 手动开始后，局进入锁定状态。
4. 锁定后不能再申请入局，不能再审核通过新成员。
5. 手动开始需要记录开始时间、开始原因、操作人。
6. 手动开始后必须创建或激活 IM 房间。

#### 验收

1. 少于 5 人时不能手动开始。
2. 达到 5 人后可按规则开始，开始后申请按钮关闭，接口也拒绝申请。
3. 后台可查看开始记录。

### 7.10 成团与局内 IM

#### 需求

1. 局达到设定人数后，系统自动成团。
2. 成团后自动创建唯一局内 IM 房间。
3. 已通过成员自动加入 IM 房间。
4. IM 房间与局 ID 绑定。
5. IM 采用自研 WebSocket 服务。
6. 一期 IM 支持文字、图片、文件传输。
7. 文件必须绑定局、房间、发送人。
8. 非本局成员不能进入房间、查看消息或下载文件。
9. 局结束后 IM 进入只读、归档或争议留存。
10. 有争议时 IM 记录不得被普通用户删除。

#### 验收

1. 同一局不会重复创建多个 IM 房间。
2. 非成员无法进入 IM。
3. 成员可发送文字、图片、文件。
4. 后台可在争议场景按权限查看 IM 和文件记录。

### 7.11 敏感词与风险预留

#### 需求

1. 后台可新增、修改、禁用敏感词。
2. IM 文本发送时进行敏感词拦截或标记。
3. 命中风险时记录风险日志。
4. 预留二期 AI 内容风险识别接口。

#### 验收

1. 命中敏感词时消息被拦截或标记。
2. 后台可查看风险日志。
3. AI 预留接口和风险日志字段存在。

### 7.12 行家进度反馈

#### 需求

1. 进行中的局允许行家提交进度反馈。
2. 进度以百分比展示，范围 0-100。
3. 系统每日提醒行家反馈进度。
4. 用户端和后台显示最新进度条。
5. 历史反馈可查看。
6. 主行家负责决定最终进度，协同行家可补充记录但不覆盖主行家进度。

#### 验收

1. 行家能提交进度百分比和说明。
2. 未反馈时系统可提醒。
3. 后台可查看历史进度反馈。
4. 主行家进度为默认展示值。

### 7.13 服务确认与评价

#### 需求

1. 局完成后进入服务确认。
2. 必要成员确认后进入评价。
3. 系统提醒所有成员评价。
4. 玩家、行家、领路人按规则互评。
5. 未参与该局的用户不能评价。
6. 未完成的局不能评价。
7. 同一评价关系不能重复评价。
8. 评价记录包含评分、标签、内容、再玩一局意向。
9. 个人中心提供可评价局入口。

#### 验收

1. 局结束后用户收到评价提醒。
2. 个人中心可找到可评价的局。
3. 重复评价被拦截。
4. 评价后成长、信用或经验数据更新。

### 7.14 成长、信用、积分与成就

#### 需求

1. 用户拥有经验值、等级、长期信用分、每日信用分、积分、成就。
2. 每日信用初始分为 100。
3. 组局人或参与人确认后退出需要扣信用分。
4. 扣分规则由后台配置。
5. 成长数据来源包括参与、发起、完成、评价、打卡、被好评、投诉、申诉处理。
6. 个人中心展示成长信息。
7. 后台可查看成长数据来源。

#### 验收

1. 确认后退出生成信用扣分记录。
2. 当日信用分从 100 基础上扣减。
3. 后台可查看扣分原因、关联局、用户、角色和时间。

### 7.15 分润、收益与支付预留

#### 需求

1. 后台可配置不同局类型的分润比例。
2. 系统可按比例自动计算金额。
3. 金额统一用分存储。
4. 分润比例用万分比存储。
5. 分润对象包括平台、行家、领路人、系统级领路人。
6. 一期免费局不接真实支付，但保留订单、分润、结算、冻结、回退、对账状态。
7. 服务未完成、评价未完成、有争议时，不进入最终结算。
8. 后台可登记线下结算记录。
9. 二期真实支付和微信分账沿用一期订单和分润状态。

#### 验收

1. 后台可维护分润模板和规则。
2. 系统可生成分润明细。
3. 后台可查看结算记录。
4. 小程序端一期不开放真实支付。
5. 二期支付预留接口和状态字段存在。

### 7.16 举报申诉

#### 需求

1. 用户可对局、成员、行家服务、领路人撮合、IM 内容、评价、分润问题提交举报或申诉。
2. 举报申诉必须关联具体局、用户、消息、订单或评价。
3. 有争议时，IM 记录保留，分润状态冻结。
4. 后台可处理申诉并填写处理结果。
5. 处理动作必须记录操作日志。

#### 验收

1. 用户可提交举报申诉。
2. 后台可查看关联证据。
3. 争议局分润被冻结或暂停。
4. 后台处理有日志。

### 7.17 个人中心

#### 需求

个人中心至少包括：

1. 个人资料。
2. 实名状态。
3. 当前角色和角色申请状态。

5. 我的局。
6. 我的入局申请。
7. 我的邀请。
8. 我的评价。
9. 可评价的局。
10. 再玩一局意向记录。
11. 经验、等级、信用、积分、成就。
12. 收益摘要和收益记录。
13. 举报申诉记录。
14. 最近足迹。

#### 验收

1. 个人中心能聚合用户核心信息。
2. 可评价入口可用。
3. 用户只能查看自己的收益和记录。

## 8. 核心业务规则

### 8.1 人数规则

1. 每局参与人数必须在 5-8 人范围内。
2. 创建局时校验人数。
3. 审核入局时再次校验人数。
4. 并发审核时以后端锁和数据库约束为准。
5. 满员后锁定入局。

### 8.2 每日开局规则

1. 每人每日最多创建 3 局。
2. 按用户和自然日统计。
3. 后台可配置每日上限。
4. 超过上限时后端拒绝创建。

### 8.3 开始规则

1. 少于 5 人时不允许开始。
2. 达到 5 人后可由发起人或主行家开始。
3. 开始后不可再加入。
4. 开始需要记录原因和操作人。
5. 开始后创建或激活 IM。

### 8.4 退出扣信用规则

1. 确认前退出不扣信用。
2. 确认后退出扣信用。
3. 开始后退出扣信用。
4. 每日信用初始分为 100。
5. 扣分值由后台配置。
6. 扣分必须关联局、用户、角色、退出阶段、扣分规则。

### 8.5 IM 权限规则

1. 一个局对应一个主 IM 房间。
2. 只有本局成员可进入。
3. 文件下载也按成员权限校验。
4. 局结束后普通成员不可继续当作普通聊天使用。
5. 争议状态下完整保留 IM。

### 8.6 分润规则

1. 分润比例配置化。
2. 免费局也可生成 0 金额或模拟分润记录。
3. 有争议时分润冻结。
4. 服务未确认或评价未完成时不进入最终结算。
5. 二期真实支付沿用一期订单和分润结构。

## 11. 非功能需求

### 11.1 安全

1. 登录态必须由后端校验。
2. 核心接口必须校验实名、角色、数据归属。
3. 管理后台必须做 RBAC 权限。
4. IM、文件、收益、实名资料都必须按权限访问。
5. 后台高风险操作必须记录操作日志。
6. 操作日志只有超级管理员可查看完整内容。

### 11.2 隐私

1. 实名信息只允许授权管理员查看。
2. IM 只允许本局成员访问。
3. 后台查看争议 IM 必须记录日志。
4. AI 预留数据应优先使用脱敏摘要和结构化事件。

### 11.3 可追溯

以下内容必须可追溯：

1. 用户邀请来源。
2. 实名审核记录。
3. 角色审核记录。
4. 局审核记录。
5. 局状态变化。
6. 入局审核记录。
7. 手动开始记录。
8. 退出扣分记录。
9. IM 消息和文件。
10. 评价和再玩意向。
11. 分润计算和结算。
12. 举报申诉处理。
13. 后台操作日志。

### 11.4 性能和稳定性

1. 首页和附近局列表必须支持分页。
2. 附近局查询应支持距离排序。
3. 入局审核、满员、建群、分润生成需要防重复。
4. IM 创建失败要有后台重试入口。
5. 导出报表采用异步任务。

| 邀请注册 | 无有效邀请码不能进入小程序，后台可查邀请关系 |
| 实名认证 | 行家和领路人可提交，后台审核后状态同步；玩家不强制实名 |
| 角色申请 | 用户可申请行家 / 领路人，审核通过后开放权限 |
| 领路人双门槛 | 条件和付费未同时满足不能开通 |
| 创建局 | 每日三局、5-8 人、实名限制生效 |
| 浏览局 | 可查看审核通过的局、附近局和同城局 |
| LBS | 300m 精度提示、手动定位、距离排序、距离角标可用 |
| 入局申请 | 可申请、可取消、可查看状态 |
| 开始规则 | 少于 5 人不能开始；达到 5 人后可开始，开始后不可再加入 |
| IM | 文字、图片、文件可用，非成员不能访问 |
| 进度反馈 | 行家可反馈，用户端展示进度条 |
| 评价 | 局结束可评价，个人中心可补评价 |
| 成长信用 | 经验、等级、信用、积分、成就可展示 |
| 收益 | 用户可查看自己的收益摘要和明细 |
| 举报申诉 | 可提交并查看处理状态 |

### 12.3 后台验收

| 模块 | 验收标准 |

### 12.4 不通过验收的情况

出现以下任一情况，不应判定一期完成：

1. 只能展示页面，核心流程无法跑通。
2. 无有效邀请码也能进入小程序或注册核心流程。
3. 未实名的行家或领路人可使用对应角色、收益或分润能力。
4. 行家、领路人无需审核即可使用。
5. 领路人未满足双门槛也能开通。
6. 人数不受 5-8 限制。
7. 每日三局限制不生效。
8. 满员或开始后仍可入局。
9. 非成员能进入 IM 或下载文件。
10. IM 没有敏感词拦截。
11. 局未完成就能评价或分润。
12. 确认后退出没有扣信用记录。
13. 分润比例写死，后台不可配置。
14. 后台无法查看审核、IM、评价、分润、申诉记录。
15. 后台关键操作没有日志。
16. 操作日志普通管理员也能完整查看。
17. 一期没有行为数据，无法支撑二期 AI 推荐。

## 13. 技术实施决策

1. 小程序端使用微信小程序技术栈，适配微信登录、定位、分享、订阅消息、文件上传。
2. PC 后台使用主流 Web 管理后台技术，适合表格、筛选、审核、配置和看板。
3. Go 业务服务负责用户、邀请、实名、角色、组局、IM、评价、LBS、后台通用接口。
4. Java 资金服务负责订单、支付预留、分润、结算、退款、对账、资金风控。
5. Python AI 服务为二期能力，一期仅预留数据和接口。
6. IM 采用自研 WebSocket，不使用第三方 IM SDK。
7. 主数据库使用 PostgreSQL，支持事务、JSON、地理数据扩展。
8. Redis 用于登录态、缓存、限流、并发锁。
9. 对象存储用于头像、实名材料、局封面、IM 文件、举报附件、导出文件。
10. 所有接口字段和数据库字段按《接口、数据库初稿.md》第 20 章执行。

## 15. 风险与依赖

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 前后端字段不一致 | 联调失败、返工 | 以《接口、数据库初稿.md》第 20 章作为定稿 |

| 行为数据缺失 | 二期 AI 无数据 | 一期开始埋点用户行为日志 |

## 17. 最终验收口径

一期验收不以“页面是否做完”为唯一标准，而以“核心业务闭环可运行、后台可管控、关键数据可追踪、二期基础可延展”为标准。

验收通过应满足：

1. 用户可被邀请进入并注册。
2. 用户可完成实名和角色审核。
3. 三类用户可按权限协作。
4. 局可创建、审核、报名、成团或手动开始。
5. 局内 IM 可安全沟通并支持文件传输。
6. 服务结束后可确认、评价、记录复玩意向。
7. 成长、信用、积分、收益记录可沉淀。
8. 后台可审核、配置、查询、处理异常。
9. 分润规则可配置，收益和结算记录可追踪。
10. 用户行为、漏斗留存、位置、评价、IM 等数据可支撑二期 AI、支付、地图和高级 IM 扩展。
