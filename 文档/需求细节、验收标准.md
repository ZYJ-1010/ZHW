# 真好玩小程序一期需求细节与验收标准

## 1. 文档目的

本文用于明确“真好玩小程序”第一期开发时需要落地的需求细节、开发注意事项、二期能力在一期需要提前打下的基础，以及第一期最终验收标准。

第一期的核心目标不是一次性完成全部生态能力，而是把“邀请海报 / 二维码 / 链接进入 -> 邀请码校验 -> 注册或登录界面分流 -> 微信登录 -> 玩家基础使用 / 行家和领路人实名认证 -> 发起 / 浏览局 -> 审核入局 -> 达到 5 人后开始或 8 人满员成团 -> 局内沟通 -> 服务确认 -> 评价成长 -> 分润记录 -> 后台管控”的主流程做成可运行、可管理、可追溯的业务系统。

第一期验收时，应重点看系统是否能支撑真实业务闭环，而不是只看页面是否齐全。

---

## 2. 一期总体建设目标

### 2.1 一期必须做到的程度

第一期需要达到以下程度：

1. 用户只能通过邀请海报、邀请二维码、邀请链接进入小程序，并完成邀请码校验、微信登录和邀请绑定。
2. 用户可以按玩家、行家、领路人三类角色使用不同功能。
3. 行家和领路人必须实名认证；玩家不要求实名认证。
4. 行家或玩家可以创建局，创建后进入后台自动审核或人工复核流程。
5. 用户可以浏览公开局、附近的局，并申请入局；小程序端不提供关键词检索。
6. 行家或发起人可以审核入局申请。
7. 局少于 5 人不允许开始，达到 5 人后可开始，8 人满员自动成团，并触发局内 IM 群。
8. 局内成员可以进行基础文字和图片沟通。
9. 局结束后，用户可以进行服务确认、评价和反馈。
10. 系统可以根据局类型、角色、会员权益生成分润记录。
11. 后台可以审核用户、角色、组局内容，并查看局、IM、评价、分润、举报申诉等记录。
12. 系统可以记录地图基础信息，实现定位、地点记录、距离显示、附近的局、动态地球和动态关系网。
13. 系统可以为二期 AI 推荐、高级 IM、真实支付分账、城市探索、用户反馈优化提前保留数据基础。

### 2.2 一期不要求做到的内容

以下内容不作为第一期正式交付目标，但第一期需要预留基础：

| 内容 | 一期处理方式 | 二期方向 |
| --- | --- | --- |
| AI 个性化推荐 | 先沉淀用户、局、评价、位置、行为数据 | 二期正式建设 AI 推荐和画像能力 |
| 音视频 IM | 一期只做文字和图片 | 二期增加音频、视频、已读未读、AI 统计 |
| 城市探索 / 足迹 | 一期只记录局地点、用户参与记录和距离 | 二期形成足迹、城市探索和地图玩法 |
| 真实支付和微信分账 | 一期可先做订单、分润、结算流程和状态设计 | 二期接入真实支付、退款、分账、对账 |
| 用户反馈深度优化 | 一期做评价、举报、申诉、基础反馈 | 二期基于真实使用数据持续优化 |

## 3. 一期核心角色需求细节

### 3.1 玩家

玩家是平台的基础用户和需求方。

#### 一期功能

1. 通过邀请海报、邀请二维码、邀请链接进入小程序。
2. 进入时自动填入唯一邀请码，并由后端校验邀请码有效性。
3. 未绑定微信的邀请码进入注册界面，已绑定唯一微信的邀请码进入登录界面。
4. 完成微信登录和邀请绑定。
3. 浏览公开局、附近的局。
4. 查看局详情，包括主题、介绍、地点、人数、状态、发起人、行家、参与规则。
5. 主动申请入局。
6. 接收领路人邀请并选择是否同意入局。
7. 入局后进入局内 IM。
8. 服务完成后确认体验。
9. 对行家、领路人、局体验进行评价。
10. 查看个人中心，包括我的局、我的申请、我的邀请、我的评价、经验、等级、信用、收益记录等。
11. 对局、成员、聊天内容或服务体验提交举报 / 申诉。

#### 开发注意事项

- 玩家不是完全无权限角色。如果玩家作为某个局的发起人，应允许其在该局范围内处理部分入局审核或服务确认。
- 玩家不能越权审核与自己无关的局。
- 玩家不强制实名认证；涉及行家、领路人、收益和分润能力时必须按对应角色校验实名认证。
- 玩家申请入局时，需要校验局状态、人数、是否已重复申请。

#### 验收标准

- 用户无邀请无法完成注册。
- 玩家可以完整走通“邀请进入 -> 微信登录 -> 浏览局 -> 申请入局 -> 入群 -> 评价”的流程。
- 玩家不能查看或操作与自己无关的局内 IM、分润明细和后台数据。
- 玩家提交举报后，后台可以查看对应举报记录。

### 3.2 行家

行家是服务提供方和局内交付主导者。

#### 一期功能

1. 玩家可提交行家申请。
2. 后台审核通过后，用户获得行家身份。
3. 行家可以创建局。
4. 行家创建的局需要提交后台审核。
5. 行家可以审核入局申请。
6. 行家可以管理自己负责局的成员准入。
7. 局成团后，行家进入局内 IM 组织服务。
8. 服务完成后，行家可以发起或确认服务完成。
9. 行家可以查看自己的局、评价、经验、信用和收益记录。

#### 开发注意事项

- 行家身份必须经过审核后才能使用。
- 行家必须完成实名认证后才能申请或开通。
- 行家只能管理自己创建或负责的局。
- 行家审核入队时，系统必须再次校验局人数，防止超员。
- 行家确认服务完成后，不应立即触发最终分润，仍需等待评价、争议判断和分润状态确认。
- 玩家邀请一名行家进入局后，该行家可作为主行家；主行家可以邀请其他行家作为协同行家。
- 局进度由主行家决定，协同行家可以补充记录但不能覆盖主行家的最终进度。

#### 验收标准

- 未审核用户不能使用行家功能。
- 未完成实名认证的用户不能使用行家功能。
- 行家可以创建局并提交审核。
- 行家可以审核入局申请。
- 行家无法管理不属于自己的局。
- 行家服务完成后，系统可进入评价和分润记录流程。

### 3.3 领路人

领路人是资源撮合者和人脉连接者。

#### 一期功能

1. 用户可提交领路人申请。
2. 后台审核通过后，用户获得领路人身份。
3. 领路人可以邀请玩家入局。
4. 领路人可以查看自己撮合的局和用户。
5. 领路人可以跟进局进度。
6. 服务完成后，领路人可以参与评价和反馈。
7. 系统可以为领路人生成分润记录或撮合记录。

#### 开发注意事项

- 领路人不等同行家，不应拥有完整的局管理权。
- 领路人必须完成实名认证后才能申请或开通。
- 领路人可以撮合和跟进，但不能越权修改局核心规则。
- 领路人邀请玩家入局后，仍需要进入行家或发起人终审流程。
- 领路人的撮合关系需要被记录，为分润和二期关系链推荐做基础。

#### 验收标准

- 未审核用户不能使用领路人功能。
- 未完成实名认证的用户不能使用领路人功能。
- 领路人可以邀请玩家入局。
- 玩家同意邀请后，系统生成入局申请或待审核记录。
- 领路人可以查看自己的撮合记录。
- 领路人不能越权管理非自己权限范围内的局。

### 3.4 管理员

管理员负责平台运营、审核、规则配置和异常处理。

#### 一期功能

1. 管理员登录后台。
2. 用户管理。
3. 实名认证审核。
4. 行家审核。
5. 领路人审核。
6. 组局内容审核。
7. 组局订单和状态查看。
8. 分润规则和分润记录查看。
9. 会员等级和权益配置。
10. 敏感词配置。
11. 举报申诉处理。
12. 基础数据看板。
13. 操作日志查看。

#### 开发注意事项

- 后台必须做权限分级，不应所有管理员都能修改分润规则和核心配置。
- 审核动作必须留痕，包括审核人、审核时间、结果、驳回原因。
- 后台能查到用户端关键业务记录，否则上线后无法运营。
- 后台需要支持异常处理，包括 IM 创建失败、分润失败、争议冻结、退款 / 回退记录等。

#### 验收标准

- 管理员可以完成所有核心审核动作。
- 所有审核、配置、人工处理动作都有操作日志。
- 后台可以按用户、局、订单、分润、申诉维度查询数据。
- 普通管理员不能越权修改高风险配置。

## 4. 一期功能需求细节

### 4.1 邀请注册

#### 需求细节

1. 用户必须通过邀请海报、邀请二维码、邀请链接三种形式之一进入小程序。
2. 每个邀请入口都必须携带唯一邀请码，不提供无码进入。
3. 系统需要校验邀请码是否有效、是否过期、是否禁用、是否已绑定微信身份。
4. 用户通过邀请进入后，小程序自动把邀请码写入邀请码输入框。
5. 邀请码未绑定微信身份时，展示注册界面。
6. 邀请码已绑定唯一微信身份时，展示登录界面。
7. 微信登录后，系统创建或识别用户账号。
8. 首次注册时，系统写入邀请人、被邀请人、邀请码和微信身份的永久绑定关系。
9. 邀请关系应记录邀请人、被邀请人、微信身份、邀请时间、邀请渠道、绑定状态。
10. 普通用户不能自行修改邀请关系。
11. 后台如需修改邀请关系，必须有权限控制和操作日志。

#### 开发注意事项

- 邀请关系会影响信任链、人脉、分润和二期关系链推荐，一期必须记录准确。
- 邀请码不应只存在前端参数里，必须由后端校验并落库。
- 同一用户重复进入不同邀请入口时，需要有明确规则。建议首次有效绑定为准，后续变更需后台审核。
- 注册界面和登录界面必须区分：注册界面用于未绑定微信的邀请码，登录界面用于已绑定唯一微信的邀请码。

#### 二期基础预留

- 需要保留邀请链路数据，为二期关系链、领路人撮合推荐、用户画像提供基础。
- 需要记录邀请渠道，区分海报、二维码、链接，为后续运营分析、裂变效果统计提供基础。

#### 验收标准

- 无有效邀请码时，用户不能进入小程序。
- 通过海报、二维码、链接进入时，邀请码能自动写入输入框。
- 未绑定微信的邀请码进入注册界面，已绑定唯一微信的邀请码进入登录界面。
- 用户注册后，后台能查到邀请人、被邀请人、微信身份、邀请时间和绑定状态。
- 邀请关系建立后，普通用户无法自行修改。
- 后台修改邀请关系时，系统记录操作日志。

### 4.2 实名认证

#### 需求细节

1. 行家和领路人提交实名信息和认证资料。
2. 认证资料进入后台自动审核或人工复核状态。
3. 管理员可以通过或驳回认证。
4. 驳回时必须填写原因。
5. 用户端展示认证状态：未认证、审核中、已通过、已驳回。
6. 已驳回用户可重新提交。
7. 玩家不要求实名认证；未认证或审核未通过的行家和领路人不能进入对应角色、收益和分润流程。

#### 开发注意事项

- 身份证号、手机号、认证图片等属于敏感信息，需要加密或私有存储。
- 后台展示实名资料时，需要做权限控制。
- 用户认证状态必须由后端控制，不能由前端页面判断。

#### 二期基础预留

- 后续若接入第三方实名接口，需要保留认证记录表、认证状态、认证来源字段。
- 二期支付和分账需要用户实名基础，一期应保证实名数据结构完整。

#### 验收标准

- 用户可提交实名资料。
- 后台可审核实名资料并填写驳回原因。
- 用户端可查看认证状态。
- 未通过认证的行家和领路人不能进入需认证的核心流程。
- 后台可查看认证记录和审核日志。

### 4.3 角色申请与权限

#### 需求细节

1. 玩家为基础身份。
2. 用户可申请成为行家。
3. 用户可申请成为领路人。
4. 行家和领路人均需后台审核。
5. 一个用户可以拥有多个角色，但操作时需要明确当前身份和权限。
6. 系统按角色展示不同功能入口。
7. 后端所有关键接口需要校验角色权限。

#### 开发注意事项

- 权限不能只靠前端隐藏按钮，必须由后端接口校验。
- 用户同时拥有多个角色时，需要避免权限混乱。
- 管理员权限也需要分级，普通运营不应能修改分润、会员、系统规则等关键配置。

#### 二期基础预留

- AI 推荐会根据角色身份推荐不同内容，一期要沉淀角色身份、申请、审核、服务数据。
- 领路人撮合能力需要依赖一期角色与邀请关系数据。

#### 验收标准

- 用户可提交行家 / 领路人申请。
- 后台可审核通过或驳回。
- 通过后用户端开放对应功能。
- 未通过角色审核的用户不能使用对应功能。
- 后端接口能拦截越权操作。

### 4.4 创建局

#### 需求细节

创建局需要支持以下信息：

| 字段 | 要求 |
| --- | --- |
| 局标题 | 必填，用于列表和详情展示 |
| 局类型 | 必填，如免费局、标准局、公益局、AA 局、众筹局、押金局 |
| 局主题 | 必填，用于分类和后续推荐基础 |
| 局介绍 | 必填，说明服务内容和参与方式 |
| 发起人 | 系统自动记录 |
| 发起人角色 | 系统自动记录玩家 / 行家 |
| 人数限制 | 必须在 5-8 人范围内 |
| 地点信息 | 支持填写或选择地点 |
| 经纬度 | 地图能力必需 |
| 是否收费 | 区分免费局和有偿局 |
| 审核状态 | 待审核、通过、驳回 |
| 局状态 | 草稿、待审核、招募中、已成团、进行中、待确认、已完成、已取消 |

#### 开发注意事项

- 单个玩家或行家自然日最多发起 3 局。
- 创建后必须进入后台审核，不应直接展示。
- 每个局需要保留状态流转日志。
- 局是后续 IM、评价、分润、地图、AI 推荐的核心对象，字段必须完整。

#### 二期基础预留

- AI 推荐需要局标题、主题、介绍、地点、价格、人数、历史成局率等数据。
- 城市探索需要局和地点绑定。
- 真实支付需要局类型、收费规则、订单状态基础。

#### 验收标准

- 用户可以创建局并提交审核。
- 每日发局上限生效。
- 人数限制只能选择或填写 5-8 人范围。
- 未审核通过的局不展示给普通用户。
- 后台可查看局详情并审核。

### 4.5 局审核

#### 需求细节

1. 用户提交局后，局进入待审核。
2. 后台审核内容包括主题、介绍、服务内容、地点、行家资质、领路人身份、违规风险。
3. 审核通过后进入招募中。
4. 审核驳回后返回修改。
5. 用户修改后可以重新提交。

#### 开发注意事项

- 审核通过前不能进入公开列表。
- 修改核心内容后应重新审核。
- 审核记录必须保留。

#### 二期基础预留

- 后续 AI 推荐和内容排序必须过滤审核未通过的局。
- 审核结果可作为内容质量和风控数据。

#### 验收标准

- 后台可以审核通过或驳回局。
- 驳回原因可在用户端展示。
- 审核通过后，局进入招募中并可被浏览。
- 后台可查看审核历史。

### 4.6 入局申请与领路人邀约

#### 需求细节

1. 玩家可主动申请加入公开局。
2. 领路人可邀请玩家入局。
3. 玩家同意邀请后，进入入局申请或待审核状态。
4. 行家或发起人审核入局申请。
5. 审核通过后，用户加入局成员列表。
6. 审核拒绝后，用户不能进入该局。
7. 用户可取消待审核申请。

#### 开发注意事项

- 入局申请需要校验局状态、人数、用户实名、是否重复申请。
- 收费局一期即使不接真实支付，也要预留支付状态字段。
- 领路人邀约不能绕过行家终审。

#### 二期基础预留

- 二期 AI 推荐领路人撮合对象，需要记录领路人邀请、用户响应、最终是否入局。
- 真实支付接入时，需要把入局申请和支付订单关联。

#### 验收标准

- 玩家可以主动申请入局。
- 领路人可以邀请玩家。
- 行家或发起人可以审核申请。
- 重复申请被系统拦截。
- 人数已满后不允许继续通过申请。

### 4.7 成团与满员触发 IM

#### 需求细节

1. 系统统计已通过成员人数。
2. 达到设定成团人数后，局状态变为已成团。
3. 系统自动创建局内 IM 群。
4. IM 群与局 ID 绑定。
5. 已通过成员自动加入 IM 群。
6. 局进入服务协作阶段。

#### 开发注意事项

- 满员判断必须由后端完成，不能由前端判断。
- 需要使用锁或幂等机制防止重复建群。
- IM 采用自研 WebSocket 服务，创建失败时需要记录状态并支持重试。
- 已成团后如有成员退出，需要按取消 / 赔付 / 后台处理规则执行，不应直接删除流程记录。

#### 二期基础预留

- 二期高级 IM、音视频、AI 统计都依赖一期 IM 与局 ID 的绑定关系。
- 后续 IM 风险预警需要一期保留基础消息记录和局状态。

#### 验收标准

- 局达到人数后，状态自动变为已成团。
- 系统自动创建该局专属 IM 群。
- 同一局不会重复创建多个 IM 群。
- 非本局成员无法进入 IM 群。
- IM 创建失败时，后台可查看失败状态并重试。

### 4.8 局内 IM

#### 需求细节

一期 IM 采用完全自研 WebSocket 服务，不使用腾讯云 IM、环信、融云等第三方 IM SDK。这样可以把局内消息、归档、争议证据和后续 AI 分析入口掌握在平台系统内。

一期 IM 范围：

| 功能 | 一期要求 |
| --- | --- |
| 文字消息 | 必须支持 |
| 图片消息 | 必须支持 |
| 文件传输 | 不作为一期必须项，可预留 |
| 语音 / 视频 | 二期 |
| 好友私聊 | 不做 |
| 长期社群 | 不做 |
| 敏感词拦截 | 必须支持 |
| 后台争议查看 | 必须支持 |

#### 开发注意事项

- IM 只服务局内沟通，不做普通社交聊天。
- 群与局强绑定。
- Go 服务负责 IM 网关、房间成员校验、消息入库和归档状态。
- IM 通讯使用 WSS 加密传输，用户进入房间前必须校验登录态和局成员关系。
- 消息需要保存发送人、局 ID、消息类型、发送时间、消息序列号、发送状态。
- 消息访问必须按成员权限控制。
- 局结束后关闭新消息发送，并进入评价确认阶段。
- 有争议时，IM 记录不得被普通用户删除。

#### 二期基础预留

- 二期音视频、已读未读、AI 统计都依赖一期消息结构和成员关系。
- 二期 IM 分析需要消息时间、发送人、消息类型、局 ID 等基础字段。
- 二期 AI 分析可通过自研 IM 的消息事件队列读取脱敏消息或摘要数据，用于风险预警、服务复盘和推荐优化。

#### 验收标准

- 成团后成员可以发送文字和图片。
- 非成员无法查看局内消息。
- 敏感词可被拦截或标记。
- 局结束后进入评价阶段，IM 不再作为普通聊天继续扩展。
- 后台可按权限查看争议局的 IM 记录。

### 4.9 IM 留存、归档与争议处理

#### 需求细节

| 局状态 | IM 处理 |
| --- | --- |
| 进行中 | 正常保存消息，成员可查看 |
| 局结束但未评价完成 | 继续保存，等待评价确认 |
| 已评价且无争议 | 前端不再展示完整聊天，可归档或定期清理 |
| 有举报 / 申诉 / 差评争议 | 保留完整记录，后台可按权限查看 |
| 争议处理完成 | 按平台保留周期归档或清理 |

#### 开发注意事项

- 不能在局结束后立即物理删除全部消息。
- 普通用户不能删除影响争议处理的消息记录。
- 后台查看、导出、归档、清理 IM 记录都需要操作日志。

#### 二期基础预留

- 二期 IM AI 分析需要基于一期留存机制提取统计数据。
- 二期后台风险预警需要识别争议局和高风险消息。

#### 验收标准

- 局结束后 IM 按状态进入留存或归档。
- 有争议局的 IM 记录不会被普通用户删除。
- 后台可查看争议相关消息。
- IM 清理或归档有操作日志。

### 4.10 服务确认与评价

#### 需求细节

1. 局进行完成后，行家发起服务完成确认。
2. 玩家确认服务体验。
3. 系统提醒所有成员评价。
4. 玩家、行家、领路人可按规则互评。
5. 评价记录写入用户信用和成长数据。
6. 用户可表达是否愿意再玩一局。
7. 差评或争议进入举报 / 申诉流程。

#### 开发注意事项

- 未参与该局的用户不能评价。
- 未完成的局不能评价。
- 同一评价关系不能重复评价。
- 评价结果不仅用于展示，也用于经验、信用和二期推荐基础。

#### 二期基础预留

- AI 推荐需要使用评价、复玩意向、服务完成情况作为核心数据。
- 手机端体验优化需要沉淀评价和反馈内容。

#### 验收标准

- 完成局后可进入评价流程。
- 未参与用户无法评价。
- 重复评价被拦截。
- 评价后用户经验、信用或成长记录更新。
- 后台可查看评价记录和争议反馈。

### 4.11 成长、信用、经验与足迹基础

#### 需求细节

一期至少记录：

- 参与次数。
- 发起次数。
- 成功成局次数。
- 服务完成次数。
- 评价得分。
- 经验值。
- 等级。
- 信用记录。
- 成就记录。
- 足迹记录。

#### 开发注意事项

- 经验和等级应来自真实行为，不应手工随意填写。
- 足迹一期不需要做城市探索玩法，但需要记录用户参与过的局和地点。
- 信用记录应关联评价、投诉、申诉、取消等行为。

#### 二期基础预留

- 二期 AI 用户画像需要行为、评价、位置、参与记录。
- 二期城市足迹需要一期记录参与地点和局地点。
- 二期推荐排序需要信用、评价、活跃度等基础数据。

#### 验收标准

- 用户完成参与、发起、评价等行为后，系统生成对应成长记录。
- 个人中心可展示经验、等级、信用、成就或基础足迹。
- 后台可查看用户成长和信用数据来源。

### 4.12 分润与收益记录

#### 需求细节

一期需要建立分润规则和收益记录能力。

| 分润模板 | 平台 | 行家 | 领路人 | 系统级领路人 | 说明 |
| --- | ---: | ---: | ---: | ---: | --- |
| 免费局 | 0 | 0 | 0 | 0 | 免费局不触发收益 |
| 标准局 | 10% | 40% | 40% | 10% | 默认收费局模板 |
| 公益局 | 0% | 100% | 0% | 0% | 仅平台发起 |
| AA 局 | 2.50% | 90% | 5% | 2.50% | 成本分摊 |
| 众筹局 | 2.50% | 90% | 5% | 2.50% | 项目启动 |
| 押金局 | 2.50% | 0% | 5% | 2.50% | 90%进入押金相关处理 |

#### 开发注意事项

- 分润比例必须配置化，不应写死。
- 金额计算应以“分”为单位，避免小数误差。
- 服务未完成、评价未完成、有争议时，不应进入最终分账。
- 一期如果不接真实支付，也要建立订单、待结算、分润明细、异常状态。
- 用户端应区分“待结算收益”和“已到账收益”。

#### 二期基础预留

- 二期真实支付和微信分账需要沿用一期订单、评价、争议、分润、对账状态。
- 多行家、多领路人、SaaS 商家特殊比例需要在一期数据结构中预留。

#### 验收标准

- 后台可配置分润模板。
- 局完成后，系统可生成分润明细。
- 用户可查看收益记录。
- 后台可查看每个局对应的分润明细。
- 有争议的局不会进入最终分账状态。

### 4.13 分账合规流程基础

#### 需求细节

一期补充说明要求分账按微信支付分账能力设计。即使一期不接真实支付，也要保证流程设计正确。

主流程为：

```text
用户支付
  ↓
服务完成
  ↓
评价确认
  ↓
争议处理
  ↓
发起分账
  ↓
查询结果
  ↓
对账归档
```

#### 开发注意事项

- 平台不应自建资金池或用户余额互转体系。
- 分账接收方需要先配置接收方身份。
- 分账状态需要包括未支付、已支付、待评价、争议处理中、待分账、分账中、分账成功、分账失败、分账回退中、已退款、已完结。
- 后台需要记录支付、退款、分账、回退、失败重试和对账记录。

#### 二期基础预留

- 二期接入真实微信支付时，需要补充微信订单号、商户订单号、回调状态、分账单号、退款单号、对账记录。
- 二期对账能力依赖一期订单和分润状态设计。

#### 验收标准

- 系统存在完整的支付 / 分润 / 分账状态设计。
- 后台可以查看订单、分润规则、接收方、分润明细、异常状态。
- 一期不接真实支付时，也能模拟从服务完成到待结算收益的流程。
- 不存在用户余额互转、平台钱包支付等高风险功能。

### 4.14 会员权益

#### 需求细节

一期需要建立会员等级与分润资格的关联。

| 会员等级 | 费用 | 权益 |
| --- | ---: | --- |
| 基础会员 | 515 | 40% 个人引荐分成，仅基础主动引荐 |
| 高级会员 | 10000 | 40% 个人分成 + 被动引荐 + 专属数据报表查看权限 |
| 尊享合伙人 | 39800 | 10% 直属团队分成 + 团队管理工具 |

#### 开发注意事项

- 会员权益应配置化。
- 分润计算前需要判断会员等级和权益有效期。
- 会员变更需要保留日志。

#### 二期基础预留

- 二期支付和分账会依赖会员资格。
- 二期 AI 推荐可结合会员等级和活跃度。

#### 验收标准

- 后台可维护会员等级和权益。
- 用户端可查看会员等级。
- 分润记录能关联会员资格。

### 4.15 LBS 与地图基础能力

#### 需求细节

一期地图范围只包括基础能力：

1. 用户定位授权。
2. 创建局时填写或选择地点。
3. 后端保存局的经纬度、城市、地址名称。
4. 局列表展示用户与局地点的大致距离。
5. 支持按距离展示或筛选附近可参与的局。

#### 开发注意事项

- 定位必须经过用户授权。
- 不记录用户实时轨迹。
- 展示的是局地点，不是用户个人位置。
- 创建局地点需要保存标准化地址和经纬度。
- 定位失败时，应提供手动选择城市或地点的兜底方式。

#### 二期基础预留

- 二期城市探索需要地点、城市、参与足迹数据。
- 二期 AI 推荐需要位置偏好和附近参与记录。
- 二期足迹功能需要记录用户参与过的局和地点。

#### 验收标准

- 用户授权后可获取当前位置。
- 创建局时可填写或选择地点。
- 局列表可展示大致距离。
- 附近的局可按距离展示或筛选。
- 后台可查看局地点信息。

### 4.16 个人中心

#### 需求细节

个人中心需要聚合用户在平台内的身份、关系、收益和成长状态。

一期包括：

- 个人信息。
- 实名认证状态。
- 当前角色。
- 会员等级。
- 我的局。
- 我的申请。
- 我的邀请。
- 我的人脉。
- 我的收益。
- 经验等级。
- 成就。
- 信用。
- 积分。
- 举报申诉。

#### 开发注意事项

- 个人中心不是简单资料页，而是用户查看自己业务状态的总入口。
- 我的局需要区分我发起的、我参与的、我撮合的。
- 收益需要区分待结算、已到账、异常或冻结。

#### 二期基础预留

- 二期用户反馈优化需要基于个人中心入口沉淀问题反馈。
- 二期 AI 推荐需要用户行为和偏好数据。

#### 验收标准

- 用户可以查看自己全部核心状态。
- 我的局、我的申请、我的邀请、我的收益能正确展示。
- 举报申诉入口可用。

### 4.17 举报申诉

#### 需求细节

用户可以对以下对象提交举报或申诉：

- 局内容。
- 局成员。
- 行家服务。

- 后台处理申诉需要记录处理人、处理时间、处理结果。

#### 二期基础预留

- 二期 IM AI 风险预警需要基于举报、申诉、差评数据。
- 二期服务质量分析需要沉淀争议类型和处理结果。

#### 验收标准

- 用户可提交举报申诉。
- 后台可查看和处理举报申诉。
- 申诉关联的 IM、评价、订单记录可被后台查看。
- 处理结果有日志。

### 4.18 数据看板与后台管控

## 5. 一期开发时必须注意的细节

### 5.1 状态机必须先设计清楚

需要明确以下状态：

| 对象 | 状态 |
| --- | --- |
| 实名认证 | 未认证、审核中、已通过、已驳回 |
| 角色申请 | 未申请、审核中、已通过、已驳回、已禁用 |
| 局 | 草稿、待审核、招募中、已成团、进行中、待确认、已完成、已取消、已关闭、申诉中 |
| 入局申请 | 待审核、已通过、已拒绝、已取消 |
| IM | 待创建、创建中、创建成功、创建失败、已归档 |
| 订单 / 分账 | 未支付、已支付、待评价、争议处理中、待分账、分账中、分账成功、分账失败、分账回退中、已退款、已完结 |
| 举报申诉 | 待处理、处理中、已处理、已关闭 |

验收时，应检查状态是否能按规则流转，异常状态是否有处理入口。

### 5.2 权限必须后端控制

- 前端隐藏按钮不等于权限控制。
- 后端接口必须校验登录态、角色、数据归属。
- 后台管理员需要分级权限。
- 分润、规则、审核、申诉处理属于高风险操作，需要操作日志。

### 5.3 分润和分账不能写死

- 分润规则需要配置化。
- 金额需要用整数“分”计算。
- 服务未完成或存在争议时，不进入最终分账。
- 一期即便不接真实支付，也要建立订单、收益、待结算、异常状态。

### 5.4 IM 必须与局绑定

- 一个局对应一个 IM 群。
- 满员或成团后创建 IM 群。
- 群成员来自局成员关系。
- IM 采用自研 WebSocket 服务，消息数据由平台自有服务器存储和管理。
- 局结束后，IM 进入评价、归档或争议留存流程。

### 5.5 地图只做基础能力，但数据要完整

- 一期不做复杂地图玩法。
- 必须保存地点、城市、经纬度。
- 必须支持距离显示和附近的局。
- 需要为二期足迹、城市探索、AI 位置推荐留数据。

### 5.6 二期能力不能混入一期交付，但一期要预留数据

一期不要把 AI、高级 IM、真实支付、城市探索全部做完，但必须为它们准备以下基础：

| 二期能力 | 一期需要打下的基础 |
| --- | --- |
| AI 推荐 | 用户资料、角色、兴趣、浏览、报名、入局、评价、位置、信用、复玩意向 |
| IM AI 分析 | IM 与局绑定、消息记录、发送人、时间、消息类型、争议状态 |
| 高级 IM | 自研 IM 网关、群 ID、成员关系、消息结构、消息权限 |
| 城市探索 / 足迹 | 局地点、经纬度、城市、用户参与记录、完成记录 |
| 真实支付 / 分账 | 订单状态、分润规则、收益记录、争议冻结、对账字段 |
| 手机端反馈优化 | 评价、举报、申诉、反馈入口、操作日志、转化数据 |

## 6. 一期验收总标准

### 6.1 主流程验收

第一期必须完整跑通以下流程：

```text
唯一邀请进入
  ↓
玩家基础使用 / 行家和领路人实名认证
  ↓
申请行家 / 领路人身份
  ↓
后台审核
  ↓
创建局
  ↓
后台审核局
  ↓
用户申请 / 领路人邀约入局
  ↓
行家或发起人审核入局
  ↓
达到人数后成团
  ↓
自动创建局内 IM
  ↓
局内沟通
  ↓
服务确认
  ↓
评价反馈
  ↓
生成经验、信用、收益 / 分润记录
  ↓
后台查看全链路记录
```

如果上述流程任何一个核心节点无法操作、无法记录或无法在后台追踪，则不应视为一期验收通过。

### 6.2 小程序端验收标准

| 入局申请 | 可申请入局，状态可追踪 |
| 领路人邀约 | 领路人可邀请玩家，玩家可确认 |
| 局内 IM | 成团后可发送文字和图片 |

| 评价 | 参与者可评价，未参与者不能评价 |

| 模块 | 验收标准 |
| --- | --- |
| 管理员登录 | 管理员可登录后台 |
| 权限管理 | 不同管理员权限有区分 |
| 用户管理 | 可查看用户资料、认证、角色、邀请关系 |

| 行家审核 | 可审核行家申请 |

### 6.4 数据和安全验收标准

| 项目 | 验收标准 |
| --- | --- |
| 敏感信息 | 手机号、实名资料等敏感数据不明文暴露给无权限人员 |
| 文件资料 | 认证资料、聊天图片等通过私有存储或权限控制访问 |
| 接口权限 | 未登录、未认证、无角色、非成员访问被拒绝 |
| IM 权限 | 非本局成员无法进入或查看 IM |
| 分润权限 | 用户只能查看自己的收益，后台按权限查看全量 |
| 操作日志 | 后台关键操作可追溯 |
| 异常记录 | 支付、分润、IM 创建、审核、申诉等异常有记录 |

### 6.5 二期基础验收标准

一期交付时，应确认以下基础已经具备：

| 二期方向 | 一期基础验收 |
| --- | --- |
| AI 推荐 | 已记录用户、角色、局、评价、位置、报名、入局、完成、信用等数据 |
| 高级 IM | IM 群与局绑定，消息有发送人、时间、类型、局 ID |
| IM AI 分析 | 争议局可保留 IM 记录，后台可按权限查看 |
| 城市探索 | 局地点有城市、地址、经纬度，用户参与记录可关联地点 |
| 真实支付分账 | 订单、分润、争议、待结算、分账状态设计完整 |
| 用户反馈优化 | 评价、举报、申诉、基础反馈数据可沉淀 |

### 6.6 不通过验收的典型情况

出现以下情况之一，不建议判定为一期验收通过：

1. 只能展示页面，核心流程无法跑通。
2. 无有效邀请码也能进入小程序或注册核心流程。
3. 未实名用户可参与收费、分润或核心组局。
4. 行家、领路人无需审核即可使用。
5. 未审核局可以公开展示。
6. 已取消局还能报名。
7. 超过人数限制仍能加入。
8. 满员后未创建 IM，或重复创建多个 IM。
9. 非本局成员能查看 IM。
10. 局未完成就能评价或分润。
11. 分润比例写死，后台无法配置。
12. 争议状态下仍自动分账。
13. 后台无法查看审核、IM、评价、分润、申诉记录。
14. 后台关键操作没有日志。
15. 地点和经纬度未记录，无法支撑附近的局和二期足迹。
16. 一期没有沉淀行为数据，无法支撑二期 AI 推荐。

## 8. 验收结论口径

第一期验收应以“核心业务闭环可运行、后台可管控、关键数据可追踪、二期基础可延展”为标准。

验收通过的标准不是页面做完，而是：

1. 种子用户可以被邀请进入。
2. 三类角色可以按权限协作。
3. 一个局可以从创建走到完成。
4. 满员后可以自动进入局内沟通。
5. 服务结束后可以评价、沉淀信用和收益记录。
6. 后台可以审核、配置、查看、处理异常。
7. 地图、IM、分润、评价、行为数据能支撑二期继续扩展。

只要这些能力稳定跑通，第一期就达到了“可上线内测、可运营验证、可继续二期扩展”的交付程度。

## 9. 一期新增必要功能补充

以下内容为一期必须纳入的必要功能，开发、接口、数据库、后台和验收均需同步覆盖。

### 9.1 达到 5 人后才允许开始

- 每局参与人数仍按 5-8 人设计。
- 如果人数少于 5 人，不允许开始。
- 达到 5 人后，发起人或主行家可以选择开始。
- 发起人开始后，局进入进行中状态，并锁定入局。
- 局开始后，不能再申请、邀约或审核新成员加入。
- 系统需要记录开始方式：满员自动开始或发起人手动开始。

验收标准：

- 少于 5 人时不能手动开始。
- 达到 5 人后可以由发起人或主行家手动开始。
- 开始后局列表和详情均显示已开始。
- 开始后用户不能再申请入局。
- 后台可以看到手动开始记录和操作人。

### 9.2 确认后退出扣信用分

- 每个用户每日初始信用分为 100 分。
- 组局人或参加人一旦确认参与，后续退出需要扣信用分。
- 退出扣分规则由后台配置。
- 扣分记录需要关联局、用户、角色、退出时间、扣分原因。

验收标准：

- 用户确认后退出，会生成信用扣分记录。
- 用户每日信用分会从 100 分基础上扣减。
- 后台可以查看信用扣分明细。
- 信用记录能进入个人成长体系。

### 9.3 行家定期反馈局进度

- 每人每日最多发起 3 局的规则保持不变。
- 局进行过程中，行家需要定期反馈局进度。
- 系统每天提醒行家反馈进度。
- 行家反馈后，局详情和后台展示百分比进度条。
- 进度反馈需要保留历史，不能只保存最后一次。

验收标准：

- 行家可以提交进度百分比和进度说明。
- 每日未反馈时系统可提醒。
- 用户端和后台都能看到当前进度。
- 后台可以查看历史进度反馈。

### 9.4 LBS 与位置能力

- 用户定位误差控制在 300m 以内。
- 如果微信授权定位误差较大，前端需要提示用户手动选择位置。
- 用户没有微信授权定位时，可以手动选择城市和位置。
- 用户可以选择自己即将前往的位置，用于提前查看附近的局。
- 支持同城筛选、附近的局推荐、距离排序、距离标签角标显示。

验收标准：

- 用户授权定位后可查看附近的局。
- 定位误差超过 300m 时有提示或兜底。
- 用户可手动选择位置。
- 局列表可按距离排序。
- 列表中每个局展示距离角标。
- 支持只看同城局。

### 9.5 分润与一期免费局边界

- 后台可以设置不同局类型的分润比例。
- 系统可以根据比例自动计算分润金额。
- 后台可以查看结算记录。
- 一期给二期真实支付预留接口和状态字段。
- 一期用户端只开放免费局。
- 后台可以直接创建任意类型的局，包括收费局、条件局、测试局，用于后台配置和二期预留。

验收标准：

- 后台可维护分润比例。
- 系统可自动生成分润明细。
- 后台可查看结算记录。
- 小程序端一期不开放真实支付。
- 后台可创建不同类型的局。

### 9.6 一期 IM 必须支持文件传输

- 一期 IM 支持文字、图片和文件传输。
- 文件必须与局、IM 房间、发送人绑定。
- 非本局成员不能查看或下载文件。
- 后台在争议处理时可按权限查看相关文件。

验收标准：

- 局内成员可以发送文件。
- 非成员无法下载文件。
- 后台能在争议场景查看文件记录。

### 9.7 敏感词库与 AI 预留

- 后台可以设置敏感词库。
- IM 消息发送时需要进行敏感词拦截或标记。
- 需要为二期 AI 自动识别敏感内容预留接口和风险日志。

验收标准：

- 后台可新增、修改、禁用敏感词。
- 命中敏感词的消息会被拦截或标记。
- 系统记录敏感内容风险日志。

### 9.8 评价提醒与再玩一局意向

- 每局结束后，系统提醒用户进行评价。
- 评价中记录是否愿意再玩一局。
- 个人中心需要提供“可评价的局”入口，方便用户后续补评价。

验收标准：

- 局结束后用户收到评价提醒。
- 用户可以在个人中心找到可评价的局。
- 评价记录包含再玩一局意向和反馈。

### 9.9 成长体系

- 一期需要具备经验值、等级、信用体系、积分、成就记录。
- 用户参与、创建、完成、评价、打卡、被好评等行为需要沉淀成长数据。

验收标准：

- 用户个人中心可查看经验、等级、信用、积分、成就。
- 后台可查看成长数据来源。
- 退出扣分、评价加分、完成局加经验均有记录。

### 9.10 领路人申请双门槛

- 申请成为领路人需要达成平台条件并完成付费。
- 如果只付费但条件未满足，需要等待条件满足。
- 如果条件满足但未付费，也不能开通。
- 条件和付费都满足后，再进入后台审核或自动开通流程。

验收标准：

- 用户端可查看领路人条件达成情况。
- 后台可配置领路人申请条件。
- 未同时满足条件和付费的用户不能开通领路人身份。

### 9.11 后台分级管理

后台角色至少包括：

| 角色 | 权限重点 |
| --- | --- |
| 超级管理员 | 全部权限，查看全部操作日志，管理管理员和高风险配置 |
| 运营管理 | 审核、内容、局状态、运营配置 |
| 用户管理 | 用户资料、实名、角色、邀请绑定关系 |
| 财务管理 | 分润比例、结算记录、二期支付预留 |
| 客户管理 | 客户资料、投诉申诉、服务跟进 |
| 数据分析员 | 用户足迹、漏斗留存、数据看板、报表导出 |
| 组局管理 | 组局审核、局列表、局状态、订单查看、后台创建局 |

要求：

- 所有管理员操作必须完整记录。
- 操作日志只有超级管理员可以查看。
- 记录管理员做了什么、什么时候做、操作前后内容、IP 和请求来源。
- 涉及报表的页面都要支持固定格式导出。

### 9.12 邀请入口设置

- 后台可以创建邀请海报、邀请二维码、邀请链接三种入口对应的邀请码。
- 后台可以设置邀请入口类型、使用次数、有效期、渠道和状态。
- 后台可以禁用邀请入口。
- 用户管理可以管理用户邀请绑定关系，但必须留操作日志。

### 9.13 漏斗留存与 AI 推荐数据基础

- 系统需要记录用户使用小程序的行为足迹。
- 包括打开小程序、浏览首页、查看局列表、查看局详情、申请入局、进入 IM、发送消息、评价、查看收益、提交申诉等。
- 数据分析员可以查看用户足迹、漏斗、留存、内容浏览统计。
- 二期 AI 推荐基于这些行为数据继续建设。

验收标准：

- 后台可以查看单个用户使用足迹。
- 后台可以查看基础漏斗和留存数据。
- 报表可以固定格式导出。
