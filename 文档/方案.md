# 真好玩小程序一期开发方案

## 1. 一期开发目标

一期开发目标是跑通“邀请注册 → 实名认证 → 发起 / 浏览局 → 审核入局 → 局内沟通 → 服务确认 → 评价成长 → 分润记录 → 后台管控”的核心业务闭环。

一期开发重点不是先做复杂生态，而是先把三类角色围绕“局”的协作流程做成可运行系统：

- 玩家能被邀请注册、浏览局、申请入局、参与沟通、确认服务、评价。
- 行家能发起局、提交审核、审核入队、组织服务、确认交付。
- 领路人能邀请用户、撮合入局、跟进局进度、形成分润记录。
- 后台能审核用户身份、行家资质、领路人身份、组局内容，并管理规则、订单、举报申诉和基础数据。

---

## 2. 系统组成

一期建议拆成四个系统层：

| 系统 | 作用 |
| --- | --- |
| 微信小程序端 | 面向玩家、行家、领路人，承载注册、认证、组局、IM、评价、个人中心 |
| PC 管理后台 | 面向运营和管理员，承载审核、用户管理、组局管理、规则配置、分润查看、举报申诉 |
| 后端 API 服务 | 统一承载账号、角色、组局、审核、IM、评价、分润、LBS、后台接口 |
| 数据与基础服务 | 数据库、文件存储、缓存、消息推送、定位、敏感词、日志 |

为什么这样拆：

小程序端负责用户体验，后台负责运营管控，后端负责业务规则和数据一致性。三者分开后，后续增加 App、SaaS 或新角色时，不需要重写核心业务。

## 3. 技术架构

### 3.1 前端架构

#### 3.1.1 微信小程序端

可采用微信原生小程序或跨端框架开发。一期如果只做微信小程序，优先使用微信原生小程序，减少跨端兼容成本。

小程序端模块：

- 登录注册模块
- 实名认证模块
- 首页 / 附近的局
- 发起局
- 局详情
- 入局申请
- 局内 IM
- 任务 / 交付确认
- 评价
- 个人中心
- 人脉 / 邀请
- 收益 / 分润记录
- 举报申诉

#### 3.1.2 PC 管理后台

后台建议采用 Vue 或 React 开发，重点是表格、审核流、详情页、配置页和数据看板。

后台模块：

- 登录与权限
- 数据看板
- 用户管理
- 实名审核
- 行家审核
- 领路人审核
- 组局审核
- 组局订单管理
- 分润规则配置
- 分润记录查看
- 会员等级配置
- 敏感词配置
- 举报申诉处理
- 系统规则配置

### 3.2 后端架构

后端采用单体优先、模块化拆分的方式开发。一期业务复杂但规模未确定，不建议一开始拆微服务。

后端模块：

- 用户中心
- 邀请关系
- 实名认证
- 角色与权限
- 组局业务
- 审核中心
- IM 消息
- 评价成长
- 分润计算
- 会员权益
- LBS 定位
- 举报申诉
- 后台管理
- 系统配置

为什么这样做：

一期需要快速跑通闭环，单体模块化更容易保证开发效率和数据一致性。后续用户量和业务边界稳定后，再把 IM、分润、消息、风控等模块独立出去。

## 4. 一期核心业务流程开发

### 4.1 邀请注册流程

开发逻辑：

1. 邀请人生成邀请海报、二维码或链接，对应唯一邀请码。
2. 被邀请人通过邀请入口进入小程序，系统自动回填邀请码。
3. 系统校验邀请码是否有效，并判断该邀请码是否已绑定唯一微信身份。
4. 未绑定微信的邀请码进入注册界面，已绑定唯一微信的邀请码进入登录界面。
5. 用户授权微信登录并创建或识别账号。
6. 系统写入邀请人与被邀请人、邀请码与微信身份的永久绑定关系。
7. 用户进入实名认证流程。

关键规则：

- 无有效邀请码不能进入小程序。
- 邀请关系创建后不可随意修改。
- 邀请关系需要记录邀请人、被邀请人、邀请码、邀请时间、邀请渠道、绑定状态和微信身份。

为什么这样做：

邀请关系会影响用户来源、信任链路和后续分润，如果注册阶段不记录清楚，后面所有关系网络和收益计算都会不稳定。

### 4.2 实名认证流程

开发逻辑：

1. 用户提交身份信息。
2. 系统保存认证资料。
3. 后台进入待审核状态。
4. 管理员审核通过或驳回。
5. 用户端展示认证状态。

认证状态：

| 状态 | 含义 |
| --- | --- |
| 未认证 | 用户尚未提交资料 |
| 审核中 | 用户已提交，等待后台审核 |
| 已通过 | 用户认证通过，可进入核心流程 |
| 已驳回 | 资料不符合要求，需要重新提交 |

为什么这样做：

原文强调真实身份和信任基础，实名认证必须成为核心业务前置条件，否则组局、收费、评价、分润都会缺少可信身份基础。

### 4.3 角色申请与审核流程

一期用户至少涉及玩家、行家、领路人三类角色。玩家为基础身份，行家和领路人需要审核后开通权限。

开发逻辑：

1. 用户提交行家或领路人申请。
2. 系统记录申请资料。
3. 后台人工审核。
4. 审核通过后开通对应角色能力。
5. 审核驳回后用户可重新提交。

角色权限：

| 角色 | 一期能力 |
| --- | --- |
| 玩家 | 浏览局、申请入局、参与协作、评价、发起需求 |
| 行家 | 发起局、审核入队、管理局内沟通、确认交付 |
| 领路人 | 邀请用户、撮合入局、跟进进度、查看撮合记录 |
| 管理员 | 审核、配置规则、管理用户、管理组局、处理申诉 |

为什么这样做：

三类角色的权限不同，如果不在系统层做角色控制，后续会出现玩家越权审核、领路人越权管理局、行家无法控制交付等问题。

## 5. 组局模块开发

### 5.1 创建局

创建局由玩家或行家发起。

一期创建局需要覆盖以下信息：

| 字段 | 说明 |
| --- | --- |
| 局标题 | 展示给用户看的名称 |
| 局类型 | 免费局、标准局、公益局、AA局、众筹局、押金局 |
| 局主题 | 对局内容方向 |
| 局介绍 | 说明本局要做什么 |
| 发起人 | 创建该局的用户 |
| 发起人角色 | 玩家或行家 |
| 人数范围 | 固定控制在 5-8 人 |
| 是否收费 | 区分免费局和有偿局 |
| 地点信息 | 用于附近的局 |
| 审核状态 | 待审核、通过、驳回 |
| 局状态 | 草稿、待审核、招募中、已成团、进行中、已完成、已取消 |

创建规则：

- 单个玩家或行家自然日最多发起 3 局。
- 每局人数控制在 5-8 人。
- 创建后进入后台审核。

为什么这样做：

局是平台最核心的数据对象。字段必须支撑审核、报名、IM、评价、分润、LBS 等后续流程，所以创建阶段要把基础信息存完整。

### 5.2 局审核

开发逻辑：

1. 用户提交局。
2. 局进入待审核状态。
3. 后台管理员查看局内容。
4. 审核通过后进入招募中。
5. 审核驳回后返回修改。

审核内容：

- 对局主题
- 服务内容
- 行家资质
- 领路人身份
- 是否存在违规风险

为什么这样做：

当前口径为后台自动审核与人工复核结合。对常规组局内容可按规则自动流转，对局主题、行家资质、领路人身份中的高风险、异常或关键材料进入人工复核；审核中心仍作为后台重点模块。

### 5.3 入局申请

玩家加入局有两种方式：

- 主动申请加入公开局。
- 被领路人邀请后同意入局。

申请流程：

1. 玩家提交入队申请。
2. 系统校验局状态和人数。
3. 如为收费局，记录费用相关状态。
4. 行家或发起人审核申请。
5. 审核通过后加入成员列表。
6. 人数满足条件后进入成团流程。

入队状态：

| 状态 | 含义 |
| --- | --- |
| 待审核 | 玩家已申请，等待审核 |
| 已通过 | 可以进入局 |
| 已拒绝 | 不允许进入 |
| 已取消 | 玩家主动取消申请 |

为什么这样做：

组局不是普通报名，服务型场景需要发起方确认人员是否合适。入局审核可以减少需求不匹配和局内协作风险。

### 5.4 成团与开群

开发逻辑：

1. 系统统计已通过成员数量。
2. 人数达到设定要求后，局进入已成团状态。
3. 系统自动创建局内 IM 群。
4. 成员自动加入群聊。
5. 局进入服务协作阶段。

为什么这样做：

局满员后才开启正式协作，可以避免未成团时产生无效沟通。IM 群和局状态绑定，便于后续追踪服务过程。

### 5.5 局状态流转

一期建议按以下状态流转开发：

```text
草稿
  ↓
待审核
  ↓
招募中
  ↓
已成团
  ↓
进行中
  ↓
待确认
  ↓
已完成
```

异常状态：

```text
审核驳回
已取消
已关闭
申诉中
```

为什么这样做：

组局流程长，涉及多人协作、审核、IM、评价、分润。必须用状态机管理，否则后续很容易出现已取消还能入局、未完成就结算、未成团就开群等问题。

## 6. IM 模块开发

一期 IM 只做局内沟通，不做复杂社交聊天。IM 功能由平台自研实现，不使用腾讯云 IM、环信、融云等第三方 IM SDK，便于后续接入平台自有 AI 分析能力。

### 6.1 功能范围

- 文字消息
- 图片消息
- 文件传输
- 敏感词拦截
- 群成员列表
- 消息时间线
- 基础消息状态

### 6.2 IM 与局绑定

每个局成团后生成一个 IM 群，群与局 ID 绑定。只有该局成员、行家、相关领路人和管理员可按权限查看或参与。

### 6.3 消息数据

核心消息字段：

| 字段 | 说明 |
| --- | --- |
| message_id | 消息 ID |
| room_id | 群 ID |
| game_id | 局 ID |
| sender_id | 发送人 |
| message_type | 文本、图片、文件 |
| content | 消息内容 |
| file_url | 文件地址 |
| created_at | 发送时间 |
| audit_status | 敏感词处理状态 |

为什么这样做：

局内沟通是服务过程的一部分，消息和局绑定后，后续处理争议、申诉、复盘时才有依据。

---

## 7. 评价、成长与信用模块

### 7.1 评价流程

服务完成后进入评价流程：

1. 行家确认服务完成。
2. 玩家确认服务体验。
3. 玩家、行家、领路人进行多方互评。
4. 系统记录评价结果。
5. 更新经验、等级、信用和成就。

### 7.2 成长数据

一期至少沉淀以下数据：

- 参与次数
- 发起次数
- 成功成局次数
- 服务完成次数
- 评价得分
- 经验值
- 等级
- 信用记录
- 成就记录
- 足迹记录

为什么这样做：

平台的长期价值来自信任沉淀。评价和成长数据不只是展示给用户看，也会影响后续推荐、匹配和用户判断。

## 8. 分润模块开发

### 8.1 分润模板

一期先按局类型配置固定分润模板：

| 分润模板 | 平台 | 行家 | 领路人 | 系统级领路人 | 备注 |
| --- | ---: | ---: | ---: | ---: | --- |
| 免费局 | 0 | 0 | 0 | 0 | 免费局无收费 |
| 标准局 | 10% | 40% | 40% | 10% | 默认 |
| 公益局 | 0% | 100% | 0% | 0% | 仅平台发起 |
| AA局 | 2.50% | 90% | 5% | 2.50% | 成本分摊 |
| 众筹局 | 2.50% | 90% | 5% | 2.50% | 项目启动 |
| 押金局 | 2.50% | 0% | 5% | 2.50% | 90%进押金池 |

### 8.2 分润计算流程

1. 局完成服务确认。
2. 系统读取局类型。
3. 系统读取对应分润模板。
4. 根据参与角色生成分润明细。
5. 写入分润记录。
6. 用户可在个人中心查看收益记录。
7. 后台可查看分润明细。

### 8.3 特殊分润预留

一期数据结构需要预留：

- 多个行家分配
- B 领路人邀请玩家入局但绑定 A 领路人的分配
- 平台 10% 自定义再分配
- SaaS 商家特殊比例
- 标准分润和自定义分润入口

为什么这样做：

分润是平台商业模式核心，不能只写死在代码里。即使一期先跑固定模板，也要把分润规则做成可配置数据，方便后续扩展。

## 9. 会员模块开发

一期需要建立会员等级与分润权益的关联。

会员等级：

| 会员体系 | 费用 | 权益 |
| --- | ---: | --- |
| 基础会员 | 515 | 40%个人引荐分成，仅基础主动引荐 |
| 高级会员 | 10000 | 40%个人分成 + 被动引荐 + 专属数据报表查看权限 |
| 尊享合伙人 | 39800 | 10%直属团队分成 + 团队管理工具 |

开发重点：

- 用户会员等级记录
- 会员权益配置
- 会员与分润资格关联
- 后台可维护会员等级和权益

为什么这样做：

原文明确“开通相应的会员权益才能获得相应的分润收益”。因此分润计算时必须判断用户会员等级和权益资格。

---

## 10. LBS 模块开发

一期 LBS 重点做“附近的局”。

开发逻辑：

1. 小程序获取用户定位授权。
2. 用户创建局时记录地点信息。
3. 系统根据用户当前位置查询附近的局。
4. 首页或发现页展示附近局列表。

核心数据：

- 经度
- 纬度
- 城市
- 地址名称
- 距离

为什么这样做：

平台强调线下真实连接，LBS 可以让用户优先看到附近的服务机会，降低线下参与门槛。

---

## 11. 个人中心开发

个人中心是用户资产和状态的聚合页。

一期内容：

- 个人信息
- 实名认证状态
- 当前角色
- 会员等级
- 我的局
- 我的申请
- 我的邀请
- 我的人脉
- 我的收益
- 经验等级
- 成就
- 信用
- 积分
- 举报申诉

为什么这样做：

用户在平台上的关系、收益、成长和参与记录都需要一个统一入口，否则用户无法理解自己在平台里的资产和进度。

---

## 12. 后台管理开发

### 12.1 数据看板

展示用户、组局、交易、评价等基础数据。

### 12.2 用户管理

管理用户资料、实名认证状态、角色状态、会员等级、邀请绑定关系。

### 12.3 审核中心

集中处理：

- 实名认证审核
- 行家资质审核
- 领路人身份审核
- 组局内容审核

### 12.4 组局管理

查看局列表、局详情、成员、状态、申请记录、IM 关联、评价记录、分润记录。

### 12.5 规则配置

配置：

- 每日发局上限
- 局人数限制
- 分润模板
- 会员权益
- 敏感词
- 赔付规则

### 12.6 举报申诉

处理用户对局、成员、服务、聊天内容、分润等问题的举报和申诉。

为什么这样做：

一期包含大量人工审核和运营干预，后台不是附属功能，而是保证平台能正常运行的管理中枢。

## 15. 一期开发顺序

### 15.1 第一阶段：基础能力

先开发账号、邀请、实名认证、角色权限、后台登录和基础用户管理。

原因：

这些是所有业务的前置条件。没有身份和权限，后面的组局、审核、分润都无法正确归属。

### 15.2 第二阶段：组局主流程

开发创建局、审核局、浏览局、申请入局、审核入队、成团状态流转。

原因：

组局是核心业务，必须先把局的数据结构和状态机稳定下来。

### 15.3 第三阶段：IM 与服务确认

开发局内 IM、消息、文件上传、敏感词、服务确认。

原因：

成团后需要沟通协作，IM 和服务确认连接了“入局”和“完成”两个关键节点。

### 15.4 第四阶段：评价、成长、分润

开发互评、经验等级、信用记录、分润模板、分润明细、收益查看。

原因：

这部分决定服务结束后能否沉淀信用和收益，是平台长期循环的基础。

### 15.5 第五阶段：后台完善与 LBS

完善数据看板、规则配置、举报申诉、附近的局、个人中心聚合数据。

原因：

这些能力用于支撑运营管理和用户持续使用，让一期系统从“流程能跑”变成“业务可运营”。

## 16. 开发重点与注意事项

### 16.1 状态机要先设计清楚

局状态、申请状态、审核状态、认证状态、分润状态都要有明确流转，不能只靠前端按钮判断。

### 16.2 邀请关系不能随意改

邀请关系涉及信任链和收益归属，应保留修改记录，并限制普通用户修改。

### 16.3 分润不要写死

分润比例应放在后台配置和规则表里，代码只负责读取规则和计算结果。

### 16.4 IM 要和局绑定

不要做成普通聊天。每个群必须对应一个局，消息才能服务于组局履约和后续申诉。

### 16.5 后台审核要贯穿全流程

实名认证、角色申请、组局内容、举报申诉都需要后台处理入口。

### 16.6 先保证闭环，再做复杂扩展

AI、App、SaaS、元宇宙、复杂地图能力都可以后续扩展，一期先保证邀请、组局、协作、评价、成长、分润这条链路稳定。
