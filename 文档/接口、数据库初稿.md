# 真好玩小程序一期接口与数据库初稿

## 1. 文档定位

本文作为一期正式开发前的接口与数据库初稿，依据客户原始文件 ，并结合当前项目内《需求文档.md》《方案.md》《补充说明和二期方案.md》《需求细节、验收标准.md》《项目节点.md》整理。

一期目标是先跑通完整业务闭环：

```text
邀请注册
  -> 实名认证
  -> 角色申请与审核
  -> 创建 / 浏览局
  -> 后台审核局
  -> 玩家申请入局 / 领路人邀约
  -> 行家或发起人审核入局
  -> 满员成团
  -> 自动创建局内 IM
  -> 局内沟通
  -> 服务确认
  -> 评价成长
  -> 分润 / 收益记录
  -> 后台查询、配置、申诉处理、日志追踪
```

本文先统一接口字段、状态枚举、数据库表结构。后续小程序、PC 后台、后端服务按本文对齐，避免前后端字段不一致。

## 2. 一期技术与数据原则

### 2.1 系统分层

| 系统 | 说明 |
| --- | --- |
| 微信小程序端 | 面向玩家、行家、领路人，承载注册、认证、组局、IM、评价、个人中心 |
| PC 管理后台 | 面向运营人员，承载审核、用户管理、组局管理、规则配置、分润查看、申诉处理 |
| Go 业务服务 | 用户、邀请、实名、角色、组局、IM、评价、LBS、后台通用接口 |
| Java 资金服务 | 订单、分润、分账、退款、收益、对账；一期可先做流程和记录 |
| Python AI 服务 | 二期正式建设；一期只预留用户、局、评价、位置、IM 等数据基础 |

### 2.2 数据库选择

一期主数据库建议使用 `PostgreSQL 16`，理由：

- 支持强事务，适合组局状态、入局审核、分润收益等一致性数据。
- 支持 `JSONB`，适合保存灵活配置、扩展资料、审核表单。
- 支持 `PostGIS`，适合附近的局、距离查询、城市位置数据。
- 支持索引和复杂查询，适合后台多条件筛选。

辅助组件：

| 组件 | 用途 |
| --- | --- |
| Redis | 登录态、验证码、限流、分布式锁、热门局缓存、IM 在线状态 |
| MinIO / COS | 实名材料、头像、IM 图片、附件、后台导出文件 |
| OpenSearch / Elasticsearch | 一期仅预留后台复杂搜索能力；小程序端不提供关键词检索 |

### 2.3 统一字段规范

| 规则 | 说明 |
| --- | --- |
| 主键 | 统一使用 `id`，类型建议 `bigserial` 或雪花 ID / UUID，开发时保持全局唯一 |
| 时间 | 统一使用 `created_at`、`updated_at`、`deleted_at` |
| 软删除 | 重要业务表保留 `deleted_at`，不做物理删除 |
| 金额 | 所有金额字段使用整数分，字段后缀为 `_cent` |
| 比例 | 分润比例使用 `basis_points`，10000 表示 100%，250 表示 2.5% |
| 状态 | 状态字段统一使用英文枚举，前端展示中文文案 |
| 日志 | 审核、状态流转、后台操作必须留痕 |

## 5. 小程序端接口

## 5.1 登录、邀请、账号

### 5.1.1 邀请入口预校验

`POST /api/app/invites/precheck`

请求：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `inviteCode` | string | 是 | 邀请码，来自海报、二维码或链接 |
| `entryType` | string | 是 | `poster/qrcode/link` |
| `scene` | string | 否 | 小程序二维码场景值 |

返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `valid` | boolean | 邀请码是否有效 |
| `inviteCode` | string | 回填到小程序邀请码输入框 |
| `entryType` | string | 邀请入口类型 |
| `authPageMode` | string | `register/login` |
| `boundWechat` | boolean | 是否已绑定唯一微信身份 |
| `maskedWechatName` | string | 已绑定微信的脱敏昵称，可空 |
| `reason` | string | 无效原因，可空 |

规则：

- 小程序启动必须先从海报、二维码或链接中解析 `inviteCode`。
- 预校验通过后，邀请码自动写入输入框。
- `boundWechat=false` 时展示注册界面；`boundWechat=true` 时展示登录界面。
- 无效、过期、禁用或缺失邀请码时，不允许进入小程序主流程。

### 5.1.2 微信登录

`POST /api/app/auth/wechat-login`

请求：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `code` | string | 是 | 微信 `wx.login` 返回 code |
| `inviteCode` | string | 条件 | 邀请码，新用户和未登录入口必须有 |
| `entryType` | string | 条件 | `poster/qrcode/link`，新用户和未登录入口必须有 |
| `scene` | string | 否 | 小程序二维码场景值 |
| `nickname` | string | 否 | 微信昵称 |
| `avatarUrl` | string | 否 | 微信头像 |

返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `token` | string | 登录 token |
| `user.id` | string | 用户 ID |
| `user.nickname` | string | 昵称 |
| `user.avatarUrl` | string | 头像 |
| `user.authStatus` | string | 实名状态 |
| `user.roles` | array | 已拥有角色 |
| `user.needInvite` | boolean | 是否缺少邀请 |
| `user.needRealname` | boolean | 是否需要实名 |
| `authPageMode` | string | `register/login` |
| `inviteCode` | string | 已绑定或本次使用的邀请码 |

规则：

- 新用户无有效邀请码，不允许完成注册。
- 用户通过海报、二维码、链接进入时，必须先完成邀请码预校验。
- 邀请码未绑定微信时，微信登录后创建账号并绑定该微信身份。
- 邀请码已绑定唯一微信时，微信登录必须匹配已绑定微信身份，否则拒绝进入。
- 邀请关系首次绑定后永久生效，普通用户不可修改。

## 5.5 入局申请、领路人邀约、成员管理

### 5.5.1 玩家申请入局

`POST /api/app/games/{gameId}/applications`

请求：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `applyReason` | string | 否 | 申请理由 |
| `fromGuideId` | string | 否 | 若由领路人邀约带入，记录领路人 |
| `expectedRole` | string | 否 | 默认为 `player` |

规则：

- 玩家申请入局不强制实名；行家、领路人使用对应角色能力时必须实名。

```json
{
  "event": "message.send",
  "clientMessageId": "cmsg_001",
  "roomId": "room_001",
  "messageType": "text",
  "content": "大家几点到？"
}
```

客户端发送图片消息：

```json
{
  "event": "message.send",
  "clientMessageId": "cmsg_002",
  "roomId": "room_001",
  "messageType": "image",
  "fileId": "file_001",
  "content": ""
}
```

服务端推送：

```json
{
  "event": "message.created",
  "messageId": "msg_001",
  "clientMessageId": "cmsg_001",
  "roomId": "room_001",
  "gameId": "game_001",
  "senderId": "user_001",
  "messageType": "text",
  "content": "大家几点到？",
  "createdAt": "2026-06-12T10:00:00+08:00"
}
```

规则：

- IM 只服务局内沟通，不做好友私聊和长期社群。
- 成团后自动创建 IM。
- 非成员不能连接或拉取消息。
- 局结束后关闭普通发送，进入评价和归档流程。
- 有争议时消息不得被普通用户删除。

## 8. 关键事务与一致性规则

### 8.1 创建局

1. 校验用户实名状态。
2. 校验角色权限。
3. 校验当日创建数量不超过 3。
4. 校验人数 5-8。
5. 写入 `games`、`game_locations`。
6. 写入 `game_status_logs`。
7. 提交审核后写入 `game_audit_records`。

### 8.2 审核入局

必须在同一事务中：

1. 锁定 `games` 当前行。
2. 校验局状态为 `recruiting`。
3. 校验申请状态为 `pending`。
4. 校验已通过人数小于 `max_participants`。
5. 更新申请状态。
6. 写入 `game_members`。
7. 更新 `approved_member_count`。
8. 若达到成团人数，更新 `game_status=formed`，写入状态日志，投递 IM 创建任务。

### 8.3 满员创建 IM

1. 同一 `game_id` 只能创建一个 `chat_rooms`。
2. 创建任务要幂等，重复触发不重复建房间。
3. 房间创建成功后同步 `game_members` 到 `chat_room_members`。
4. 失败写入 `create_error`，后台可重试。

### 8.4 服务确认与分润

1. 局进入 `pending_confirm` 后生成服务确认记录。
2. 全部需要确认的成员完成确认后，进入评价。
3. 有争议则 `game_status=disputed`，分润冻结。
4. 无争议且评价完成后生成 `revenue_records` 和 `revenue_record_items`。
5. 用户端展示待结算收益，后台可追踪来源。

### 8.5 举报申诉

1. 申诉必须关联具体对象。
2. 关联 IM、评价、收益、订单时要冻结或保留关键证据。
3. 后台处理必须写操作日志。
4. 处理完成后按结果决定恢复、冻结、退款、回退或关闭。

## 18. 开发默认口径与可配置项

以下内容不再作为阻塞开发的待确认问题，先按默认口径进入一期设计；后续客户如调整，按配置或变更处理。

### 19.1 达到 5 人后才可开始，开始后锁定不可再加入

规则：

1. 每局参与人数配置仍为 5-8 人。
2. 正常成团逻辑：达到设定成团人数后自动成团。
3. 少于 5 人时不允许手动选择“开始局”。
4. 达到 5 人后，发起人或主行家可手动开始。
5. 开始后，局状态进入 `in_progress`，不能继续申请、邀约或审核新成员加入。
6. 开始后需要记录开始方式：满员自动开始 / 发起人手动开始。

新增 / 调整枚举：

| 枚举 | 值 | 说明 |

| `game_start_mode` | `auto_full` | 满员自动开始 |
|  | `creator_manual` | 发起人或主行家达到 5 人后手动开始 |
| `game_status` | `in_progress` | 已开始；是否允许继续入局统一由 `join_locked` 控制 |

| `startMode` | string | 是 | `creator_manual` |
| `reason` | string | 否 | 开始原因 |

处理规则：

### 20.1 全局字段和返回规则

#### 20.1.1 ID、时间、金额、位置

| 类型 | 前端字段 | 后端 / 数据库字段 | 规则 |
| --- | --- | --- | --- |
| 主键 ID | `id` | `id` | 后端以 bigint 存储，接口统一转 string 返回，避免小程序 JS 精度丢失 |
| 用户 ID | `userId` | `user_id` | 所有用户相关接口必须带当前登录态，不能信任前端传入的当前用户 ID |
| 局 ID | `gameId` | `game_id` | 组局、IM、评价、分润、举报都必须能追溯到局 |
| 订单 ID | `orderId` | `order_id` | 一期免费局也保留订单 ID，可为空但不能影响分润模拟 |
| 金额 | `amountCent` | `amount_cent` | 全部金额用分，不用元，不用浮点 |
| 比例 | `ratioBps` | `ratio_bps` | 分润比例用万分比，10% = 1000，2.5% = 250 |
| 时间 | `createdAt` | `created_at` | 接口统一 ISO 8601 字符串，数据库用 timestamptz |
| 经纬度 | `longitude` / `latitude` | `longitude` / `latitude` | 使用 GCJ-02 坐标，保留 6 位小数 |
| 距离 | `distanceMeter` | 计算字段 | 单位米，前端显示 `distanceLabel` |
| 删除 | `deletedAt` | `deleted_at` | 核心业务表软删除，物理删除只允许清理临时文件 |

#### 20.1.2 通用分页

请求参数统一：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `pageNo` | int | 否 | 默认 1 |
| `pageSize` | int | 否 | 默认 20，最大 100 |
| `sortBy` | string | 否 | 排序字段，后端白名单校验 |
| `sortOrder` | string | 否 | `asc/desc` |

返回结构统一：

```json
{
  "code": 0,
  "message": "ok",
  "requestId": "req_20260612_xxx",
  "data": {
    "list": [],
    "pageNo": 1,
    "pageSize": 20,
    "total": 0,
    "hasMore": false
  }
}
```

#### 20.1.3 幂等和并发

| 场景 | 必须传 / 生成 | 规则 |
| --- | --- | --- |
| 创建局 | `Idempotency-Key` | 同一用户 10 分钟内重复提交同 key，只返回同一个 `gameId` |
| 申请入局 | 后端唯一约束 | 同一用户同一局只能有一条有效申请 |
| 审核入局 | `version` | 防止两个管理员 / 发起人重复审核 |
| 手动开始局 | `version` | 校验局仍处于 `recruiting`，开始后锁定 |
| 退出局 | `version` | 防止同一成员重复退出、重复扣分 |
| 服务确认 | 后端唯一约束 | 同一成员同一局只能确认一次 |
| 评价 | 后端唯一约束 | 同一评价人对同一局同一被评价人只能评价一次 |
| 分润计算 | `revenueCalcNo` | 同一局同一结算批次只能生成一次有效分润 |
| 文件上传 | `fileSha256` | 同一文件可复用文件记录，但权限仍按局成员校验 |

| 方法 | 接口 | 入参 | 返回 |

- 微信定位 `accuracyMeter` 大于 300 时，后端仍可保存，但返回 `accuracyWarning=true`。

- 距离排序必须以后端计算为准，前端不能自行排序后覆盖后端顺序。

#### 20.4.3 创建局、后台条件局、每日三局

`POST /api/app/games`

请求：

```json
{
  "title": "周末咖啡创业交流局",
  "gameType": "free",
  "coverFileId": "90001",
  "description": "局说明",
  "serviceContent": "服务内容",
  "tags": ["创业", "咖啡"],
  "minMembers": 5,
  "maxMembers": 8,
  "startAt": "2026-06-20T14:00:00+08:00",
  "endAt": "2026-06-20T17:00:00+08:00",
  "location": {
    "cityCode": "330100",
    "cityName": "杭州市",
    "address": "文三路 100 号",
    "longitude": 120.123456,
    "latitude": 30.123456
  },
  "expertUserIds": ["10002"],
  "guideUserIds": ["10003"],
  "visibility": "public"
}
```

返回：`GameDetailDTO`。

硬规则：

- 小程序端一期只允许 `gameType=free`。
- `condition` 条件局一期只能后台创建，接口为 `/api/admin/games`。
- 每人自然日最多创建 3 局，按 `creator_user_id + created_date` 统计。
- 每局 `minMembers` 和 `maxMembers` 必须在 5 到 8 之间，且 `minMembers <= maxMembers`。
- 未实名用户、被禁用用户、被风控限制用户不能创建局。
- 创建后默认 `draft` 或 `pending_audit`，是否直接提交由 `submitAudit` 控制。

#### 20.4.4 局审核后展示、申请入局

| 方法 | 接口 | 入参 | 返回 |
| --- | --- | --- | --- |
| GET | `/api/app/games` | `keyword`、`status`、`cityCode`、`tag`、分页 | `GameListItemDTO` 列表 |
| GET | `/api/app/games/{gameId}` | 无 | `GameDetailDTO` |
| POST | `/api/app/games/{gameId}/apply` | `applyReason`、`fromGuideId` | `applicationId`、`applicationStatus` |
| GET | `/api/app/game-applications/my` | `status`、分页 | 我的申请 |
| POST | `/api/app/game-applications/{applicationId}/cancel` | `cancelReason` | 最新申请状态 |
| POST | `/api/app/game-applications/{applicationId}/audit` | `auditResult`、`auditRemark`、`version` | 申请状态、成员信息 |

申请入局规则：

- 只有 `recruiting` 状态可申请。
- `locked_started`、`full_locked`、`ongoing`、`confirming`、`completed` 都不可申请。
- 同一用户同一局不能重复申请。
- 申请通过时必须再次校验人数，避免并发超员。
- 领路人邀约只产生邀请和来源关系，不能绕过发起人 / 行家的终审。

#### 20.4.5 达到 5 人后开始、开始后锁定

`POST /api/app/games/{gameId}/manual-start`

请求：

```json
{
  "version": 3,
  "startReason": "已达到5人，发起人决定开始"
}
```

返回：

```json
{
  "gameId": "20001",
  "oldStatus": "recruiting",
  "newStatus": "locked_started",
  "lockedAt": "2026-06-20T14:00:00+08:00",
  "chatRoomId": "50001",
  "currentMemberCount": 5,
  "maxMembers": 8
}
```

规则：

- 只有发起人或主行家可以手动开始。
- 当前成员数少于 5 人时不允许手动开始。
- 达到 5 人后允许开始，并记录 `start_reason`。
- 手动开始后 `canApply=false`，任何用户不能再入局。
- 手动开始必须创建或激活 IM 房间。
- 状态变化必须写 `game_status_logs`。

#### 20.4.6 退出局和扣信用

`POST /api/app/games/{gameId}/quit`

请求：

```json
{
  "quitReason": "临时有事",
  "version": 4
}
```

返回：

```json
{
  "gameId": "20001",
  "memberStatus": "quit_after_confirm",
  "deductCredit": true,
  "deductValue": -10,
  "todayCreditScore": 90,
  "creditLogId": "70001"
}
```

规则：

- 未确认前退出不扣信用，但保留记录。
- 确认后退出、开始后退出默认扣每日信用分。
- 每日信用基础分为 100，每天首次访问或定时任务初始化 `daily_credit_scores`。
- 扣分规则由后台配置，不能写死在前端。
- 发起人退出如果导致局无法继续，局进入 `cancelled` 或 `disputed`，由后台规则判定。

### 20.7 核心事务规则

#### 20.7.1 创建局事务

1. 校验登录、实名、账号状态。
2. 校验每日创建数小于 3。
3. 校验人数 5-8。
4. 校验一期小程序端只能创建免费局。
5. 写 `games`、`game_locations`、`game_status_logs`。
6. 发起人写入 `game_members`，角色为 `creator`。
7. 若 `submitAudit=true`，状态进入 `pending_audit`。
8. 提交成功后写用户行为 `game_create_submit`。

#### 20.7.2 审核入局事务

1. 校验审核人是发起人、行家或后台有权限人员。
2. 校验局状态为 `recruiting`。
3. 校验 `is_join_locked=false`。
4. 校验有效成员数未超过 `max_members`。
5. 更新 `game_applications.status=approved/rejected`。
6. 通过时写入或更新 `game_members`。
7. 如成员数达到 `maxMembers`，更新 `games.status=full_locked` 和 `is_join_locked=true`。
8. 满员或手动开始时创建 / 激活 `chat_rooms`。

#### 20.7.3 手动开始事务

1. 校验局状态为 `recruiting`。
2. 校验当前用户是发起人或具备管理权限。
3. 允许当前人数小于 `minMembers`。
4. 更新 `games.status=locked_started`、`is_join_locked=true`、`manual_started_at`。
5. 拒绝所有后续入局申请入口。
6. 创建 / 激活 IM 房间。
7. 写系统消息：局已开始，不再接受新成员。

#### 20.7.4 退出扣信用事务

1. 查询 `game_members` 当前状态。
2. 判断退出阶段：确认前、确认后、开始后。
3. 确认后和开始后退出，初始化或读取当日 `daily_credit_scores`。
4. 根据配置写 `credit_logs`，更新当日分。
5. 更新 `game_members.member_status`。
6. 如影响局继续进行，写 `game_status_logs` 并通知发起人 / 后台。

#### 20.7.5 服务完成、评价、分润事务

1. 发起服务完成确认后，写 `game_service_confirms`。
2. 每个成员确认写 `game_service_confirm_items`。
3. 全部必要成员确认后，局进入 `pending_review`。
4. 系统生成 `review_reminders`。
5. 评价完成或达到配置的评价截止条件后，进入分润计算。
6. 有举报、申诉、争议时，`revenue_records.status=frozen`。
7. 无争议时生成 `revenue_records` 和 `revenue_record_items`。

## 21. 三文档最终一致性说明

如三份文档出现冲突，按以下顺序处理：

1. 业务范围和一期是否必须做，以 `PRD.md` 与 `功能清单.md` 的 P0 / P1 标记为准。
2. 接口路径、字段名、枚举值、数据库字段，以 `接口、数据库初稿.md` 第 20 章为准。
3. 旧章节中如果出现“待确认”“只预留”“是否打开”等旧表述，凡与第 19 章、第 20 章和本章冲突，一律按第 19 章、第 20 章和本章执行。

### 21.3 开发联调禁止事项

1. 禁止前端自行判断核心权限后直接绕过后端校验。
2. 禁止把金额用元或浮点数传递，统一用分。
3. 禁止把分润比例写死，统一使用后台配置。
4. 禁止局开始后继续允许入局申请通过。
5. 禁止非局成员访问 IM 消息或文件。
6. 禁止普通管理员查看完整操作日志。
7. 禁止只做页面不落库，所有核心操作必须有接口、状态和日志。
8. 禁止删除二期 AI、支付、地图、IM 扩展所需的数据字段。
