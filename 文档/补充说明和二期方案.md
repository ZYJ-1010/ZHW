# 真好玩小程序补充说明和二期方案

## 一、一期补充说明

本补充说明不直接改动原《需求文档》和《方案》，用于后续与服务商、客户或团队沟通时补充一期边界。当前补充重点包括：分账合规流程、局内 IM 范围与留存规则、地图基础能力。

---

## 1. 分账合规流程补充

### 1.1 核心原则

项目涉及收费和分账时，分账方案按微信支付分账功能设计。平台负责配置分润规则、计算分账金额、记录订单状态、调用微信支付分账接口和同步分账结果；实际资金流转由微信支付完成。

这样处理后，平台不用私下沉淀用户资金，也不用人工向行家、领路人转账。用户付款、服务确认、评价反馈、争议处理、分账执行、分账结果查询都可以形成完整的系统闭环。

### 1.2 接入模式

本项目按微信支付普通商户分账能力设计。若后续改为服务商、电商收付通或其他平台型接入模式，需要根据对应微信支付模式调整商户号、二级商户号、AppID、接收方绑定和接口参数，但业务流程仍保持“用户支付 -> 服务完成 -> 评价确认 -> 争议处理 -> 发起分账 -> 查询结果 -> 对账归档”的主线。

### 1.3 微信支付分账前置条件

使用微信支付分账功能前，需要完成以下准备：

| 前置项 | 说明 |
| --- | --- |
| 微信支付商户号 | 平台需要具备可用于小程序支付的微信支付商户号 |
| 分账功能开通 | 商户号需要开通微信支付分账能力 |
| API 证书和密钥 | 后端需要配置微信支付 API v3 所需的商户证书、私钥、平台证书或微信支付公钥 |
| 小程序 AppID 绑定 | 小程序 AppID 需要与微信支付商户号完成绑定 |
| 分账接收方配置 | 行家、领路人等收款对象需要先按微信支付规则添加为分账接收方 |
| 支付下单分账标识 | 收费局创建微信支付订单时，需要在下单参数中标记该订单需要分账 |
| 分账比例规则 | 后台需要配置不同局类型对应的平台、行家、领路人、系统级领路人的比例 |
| 分账金额校验 | 系统需要校验分账金额不超过订单金额和微信支付最大分账比例 |
| 分账状态表 | 系统需要记录每笔订单的待分账、分账中、分账成功、分账失败、分账回退等状态 |
| 对账能力 | 后台需要能查询支付、退款、分账、解冻、回退和账单记录 |

### 1.4 分账接收方规则

分账前需要先添加分账接收方。接收方可以是商户，也可以是个人 OpenID。

| 接收方类型 | 微信支付标识 | 适用对象 | 账号规则 |
| --- | --- | --- | --- |
| 商户号 | `MERCHANT_ID` | 公司、个体户、合作商户、具备商户号的服务方 | 接收方账号为微信支付商户号 |
| 个人 OpenID | `PERSONAL_OPENID` | 个人行家、个人领路人等个人收款对象 | 接收方账号为该用户在商户 AppID 下的 OpenID |

添加分账接收方时，需要记录接收方与平台的关系类型。微信支付支持门店、员工、店主、合作伙伴、总部、品牌方、分销商、用户、供应商、自定义等关系类型。对于本项目，可按角色进行映射：

| 平台角色 | 微信支付关系类型建议 |
| --- | --- |
| 行家 | 合作伙伴、供应商或自定义 |
| 领路人 | 合作伙伴、分销商或自定义 |
| 系统级领路人 | 合作伙伴或自定义 |
| 商家 / 机构服务方 | 商户号接收方或供应商 |

涉及姓名、商户全称等敏感信息时，需要按照微信支付要求进行加密传输。若传入个人姓名，微信支付会进行实名一致性校验，不一致时可能拒绝添加或拒绝分账。

### 1.5 分账比例与金额规则

分账金额必须以“分”为单位，且只能为整数。每笔分账金额需要同时满足以下规则：

| 规则 | 说明 |
| --- | --- |
| 不超过原订单金额 | 分账金额不能超过该笔微信支付订单金额 |
| 不超过最大分账比例 | 分账金额不能超过商户在微信支付侧配置的最大分账比例 |
| 不超过剩余可分金额 | 同一订单多次分账时，不能超过该订单剩余可分金额 |
| 接收方必须有效 | 接收方必须已经添加成功，且分账关系未解除 |
| 金额必须准确 | 后端按订单金额、局类型、角色比例计算明细，并处理四舍五入后的尾差 |

本项目当前分润模板可作为后台分账规则来源：

| 分润模板 | 平台 | 行家 | 领路人 | 系统级领路人 | 说明 |
| --- | ---: | ---: | ---: | ---: | --- |
| 免费局 | 0 | 0 | 0 | 0 | 免费局不触发支付分账 |
| 标准局 | 10% | 40% | 40% | 10% | 默认收费局模板 |
| 公益局 | 0% | 100% | 0% | 0% | 仅平台发起 |
| AA局 | 2.50% | 90% | 5% | 2.50% | 成本分摊 |
| 众筹局 | 2.50% | 90% | 5% | 2.50% | 项目启动 |
| 押金局 | 2.50% | 0% | 5% | 2.50% | 90%进入押金相关处理 |

实际执行分账时，需要以微信支付商户平台配置的最大分账比例为上限。如果业务分润模板超过微信支付允许比例，系统应按微信支付规则调整或拆分业务结算方式。

### 1.6 单笔订单分账限制

微信支付分账接口对单笔订单存在次数和接收方数量限制：

| 限制项 | 规则 |
| --- | --- |
| 同一订单分账次数 | 同一笔订单最多发起 50 次分账请求 |
| 单次接收方数量 | 每次分账请求最多 50 个接收方 |
| 分账处理方式 | 分账接口为异步处理，接口受理成功不等于最终分账成功 |
| 分账结果确认 | 最终结果需要通过查询分账结果接口确认 |
| 分账单号 | 商户分账单号必须在商户系统内部唯一 |
| 幂等处理 | 同一商户分账单号重复请求，会被视为同一次分账请求 |

### 1.7 订单与分账主流程

1. 用户报名收费局，系统创建微信支付订单，并标记该订单需要分账。
2. 用户完成支付后，微信支付回调成功，系统生成支付订单和待分账记录。
3. 系统根据局类型、角色和会员权益，计算平台、行家、领路人、系统级领路人的分账明细。
4. 局成团后进入服务流程，订单保持“已支付 / 待服务完成”状态。
5. 局结束后，系统主动询问用户体验并引导所有参与方完成评价。
6. 全部评价完成且无举报、申诉或争议时，订单进入“待分账”状态。
7. 后端按订单分账明细调用微信支付分账接口，向行家、领路人等接收方发起分账。
8. 微信支付分账为异步处理，系统需要定时或按回调 / 查询结果更新分账状态。
9. 分账成功后，用户端展示订单已完成，后台展示分账完成时间、接收方、金额和结果。
10. 该订单确认不再继续分账后，系统按微信支付规则完成分账完结处理。

### 1.8 微信支付分账接口动作

| 动作 | 用途 | 关键点 |
| --- | --- | --- |
| 添加分账接收方 | 将行家、领路人等对象添加为可收款接收方 | 接收方类型包括商户号和个人 OpenID |
| 删除分账接收方 | 删除不再使用的接收方关系 | 删除后不能继续向该接收方分账 |
| 请求分账 | 对已支付订单发起分账 | 需要微信订单号、商户分账单号、接收方列表、金额、描述、是否解冻剩余资金 |
| 查询分账结果 | 查询分账是否完成 | 分账为异步处理，必须查询最终结果 |
| 解冻剩余资金 | 对不再分账的剩余金额进行解冻 | 解冻后该笔订单剩余金额回到分账发起方商户 |
| 请求分账回退 | 已分账后需要撤回资金时使用 | 需要基于原分账单和回退单号处理 |
| 查询分账回退结果 | 查询回退是否完成 | 回退处理中时使用同一回退单号继续查询 |
| 申请分账账单 | 下载分账账单用于财务核对 | 微信支付按天提供分账账单 |

### 1.9 分账请求核心参数

| 参数 | 说明 |
| --- | --- |
| `transaction_id` | 微信支付订单号，用于定位原支付订单 |
| `out_order_no` | 商户分账单号，商户系统内部唯一 |
| `receivers` | 分账接收方列表 |
| `type` | 接收方类型：`MERCHANT_ID` 或 `PERSONAL_OPENID` |
| `account` | 接收方账号：商户号或个人 OpenID |
| `name` | 接收方名称或个人姓名，涉及敏感信息时需按微信支付规则加密 |
| `amount` | 分账金额，单位为分，必须为整数 |
| `description` | 分账原因描述 |
| `unfreeze_unsplit` | 是否解冻剩余未分资金，设置为 true 后，剩余未分账金额会解冻回分账发起方，且该订单不再支持继续分账 |

本项目中，`out_order_no` 可按“订单号 + 分账批次”生成，确保同一订单多次分账时每次单号唯一；接收方列表根据后台计算出的行家、领路人、系统级领路人明细生成。

### 1.10 分账结果与失败原因

分账单状态需要以微信支付返回结果为准。

| 分账单状态 | 含义 | 处理方式 |
| --- | --- | --- |
| `PROCESSING` | 处理中，非终态 | 后台保持分账中，继续查询 |
| `FINISHED` | 分账完成，终态 | 查看每个接收方的分账结果 |

每个接收方也有自己的结果：

| 接收方结果 | 含义 | 处理方式 |
| --- | --- | --- |
| `PENDING` | 待分账，非终态 | 继续查询 |
| `SUCCESS` | 分账成功，终态 | 标记该接收方到账成功 |
| `CLOSED` | 已关闭，终态 | 记录失败原因并进入异常处理 |

常见失败原因包括：

| 失败原因 | 含义 |
| --- | --- |
| `ACCOUNT_ABNORMAL` | 分账接收账户异常 |
| `NO_RELATION` | 分账关系已解除 |
| `RECEIVER_HIGH_RISK` | 接收方风险较高 |
| `RECEIVER_REAL_NAME_NOT_VERIFIED` | 接收方未实名 |
| `NO_AUTH` | 分账权限已解除 |
| `RECEIVER_RECEIPT_LIMIT` | 超出用户月收款限额 |
| `PAYER_ACCOUNT_ABNORMAL` | 分出方账户异常 |
| `INVALID_REQUEST` | 请求参数或描述不符合规则 |

### 1.11 争议、退款与分账回退流程

如果局结束后存在争议，分账流程暂停：

1. 用户提交争议、投诉、申诉或差评问题。
2. 订单进入“争议处理中”状态。
3. 系统保留 IM 记录、评价记录、支付记录和操作日志。
4. 后台处理争议结果。
5. 如果服务确认有效，则继续进入分账流程。
6. 如果需要退款，则执行退款流程。
7. 如果已经分账后需要撤回部分资金，则按微信支付分账回退流程处理。
8. 分账回退发起后，需要查询回退结果；回退处理中时，保持原回退单号继续查询，避免重复生成不同回退单号导致资金风险。

### 1.12 分账状态设计

| 状态 | 说明 |
| --- | --- |
| 未支付 | 用户尚未完成付款 |
| 已支付 | 微信支付成功，等待服务开始或完成 |
| 待评价 | 局已结束，等待成员评价和确认 |
| 争议处理中 | 存在投诉、申诉、差评争议或人工介入 |
| 待分账 | 评价完成且无争议，可以发起分账 |
| 分账中 | 已调用微信支付分账接口，等待结果 |
| 分账成功 | 微信支付返回分账成功 |
| 分账失败 | 分账请求失败或接收方异常 |
| 分账回退中 | 已分账后需要按规则回退 |
| 已退款 | 订单已退款或部分退款 |
| 已完结 | 订单支付、评价、分账、对账全部完成 |

### 1.13 后台需要展示的分账信息

后台需要提供完整的分账管理能力，方便运营和财务查看：

| 信息 | 说明 |
| --- | --- |
| 订单信息 | 局 ID、订单号、支付单号、用户、金额 |
| 分账规则 | 局类型、分账模板、各角色比例 |
| 分账接收方 | 行家、领路人、系统级领路人及对应收款身份 |
| 分账明细 | 每个接收方的分账金额、比例、状态 |
| 微信分账结果 | 微信返回的分账单号、状态、失败原因 |
| 退款 / 回退记录 | 退款金额、回退金额、操作时间、原因 |
| 操作日志 | 后台查看、人工处理、重试、关闭等操作记录 |

### 1.15 合规与风控规则

- 资金通过微信支付完成支付和分账，平台系统负责规则计算、状态记录和对账。
- 服务未完成、评价未完成或存在争议时，不触发分账。
- 分账金额不能超过微信支付规则允许的金额和比例。
- 分账接收方需要先按微信支付要求完成绑定或授权。
- 分账涉及个人姓名等敏感信息时，按微信支付要求加密传输。
- 支付、退款、分账、解冻、回退、失败重试都需要保留后台记录。
- 用户端展示收益时，应区分“待结算收益”和“已到账收益”。
- 后台需要提供失败重试、人工处理、异常标记、对账确认等操作，但所有资金动作以微信支付返回结果为准。
- 财务对账需要结合微信支付分账账单，核对分账金额、回退金额、接收方和完成时间。

### 1.16 规则依据说明

- 微信支付小程序 / JSAPI 下单支持设置分账标识，订单支付成功后可按分账订单处理。
- 微信支付分账功能支持商户在微信订单支付成功后，将资金按规则分给分账接收方。
- 微信支付分账采用异步处理，接口受理成功不等于最终分账成功，系统需要查询分账结果。
- 微信支付分账金额受订单金额、剩余可分金额和商户最大分账比例限制。
- 微信支付分账接收方需要先按规则添加，接收方可以是商户号，也可以是个人 OpenID。
- 微信支付支持分账完结或解冻剩余资金，订单确认不再继续分账后，需要处理剩余未分资金。
- 已分账订单后续发生退款或资金撤回时，需要按分账回退流程处理。
- 微信支付提供分账账单，平台可用于财务核对和后台对账。

## 2. 局内 IM 范围与流程补充

### 2.1 一期 IM 功能范围

一期 IM 不做复杂社交聊天，只满足局内协作和争议追溯。IM 功能由平台自研实现，不使用腾讯云 IM、环信、融云等第三方 IM SDK，便于后续接入平台自有 AI 分析能力。

一期范围如下：

| 功能 | 是否一期 |
| --- | --- |
| 文字消息 | 是 |
| 图片消息 | 是 |
| 文件传输 | 否 |
| 语音 / 视频 | 否 |
| 好友私聊 | 否 |
| 长期社群 | 否 |
| 敏感词拦截 | 是 |
| 后台按权限查看争议记录 | 是 |

### 2.2 每个局的 IM 创建流程

1. 局处于招募中时，不提前开放正式 IM 群。
2. 成员达到成团条件后，系统自动创建该局专属 IM 群。
3. IM 群与局 ID 绑定，不做成普通聊天群。
4. 只有本局成员、行家、相关领路人和有权限的管理员可查看或参与。
5. 局进行中，用户可发送文字和图片，用于沟通服务安排、现场问题和交付确认。
6. 局结束后，IM 群关闭新消息发送，进入评价确认阶段。

### 2.3 局结束后的评价与留存流程

局结束后，系统需要主动询问用户对本局的感受，例如：

- 本局体验是否符合预期？
- 服务是否完成？
- 是否存在争议或需要平台介入？
- 是否愿意对本局进行评价？

推荐流程：

```text
局完成
  ↓
系统提醒所有成员评价
  ↓
全部完成评价
  ↓
判断是否存在争议
  ↓
无争议：进入分账 / 归档 / 清理流程
有争议：保留 IM 记录并进入后台申诉处理
```

### 2.4 IM 记录删除与服务器压力处理

IM 记录确实会带来服务器存储压力，局结束后立即物理删除全部消息会影响争议追溯。更合理的做法是按业务状态分层处理：

| 状态 | 处理方式 |
| --- | --- |
| 局进行中 | 正常保存消息，供成员查看 |
| 局结束但未评价完成 | 继续保存，等待评价和确认 |
| 已评价且无争议 | 前端不再展示完整聊天，可转入归档或定期清理 |
| 有举报 / 申诉 / 差评争议 | 保留完整记录，直到处理完成 |
| 争议处理完成 | 按平台隐私政策和保留周期清理或冷存储归档 |

这样既能避免聊天记录无限增长，也能保证出现矛盾时有依据可查。

### 2.5 建议写入给服务商的开发要求

服务商需要实现：

- 每个局成团后自动创建独立 IM 群。
- IM 群必须与局 ID、成员 ID、订单 ID 关联。
- 一期只开发文字和图片消息。
- 局结束后自动进入评价确认流程。
- 评价完成且无争议后，IM 记录进入归档或清理流程。
- 存在争议时，IM 记录不得被普通用户删除，后台可按权限查看。
- 后台需要记录 IM 清理、归档、查看、导出的操作日志。

## 二、二期方案

## 1. 二期建设目标

二期是在一期核心组局流程跑通后的增强版本，重点从“流程可用”升级到“体验更好、推荐更准、玩法更丰富、交易更真实”。

二期需要围绕 AI 个性化推荐、高级 IM、城市探索特色玩法、真实支付与分账、用户反馈优化等方向进行完善，通过功能矩阵的补充，优化用户操作流程，提升内容的个性化与趣味性，从而增强用户的平台使用粘性与活跃度。

二期会正式引入 AI 能力，本方案主要说明 AI 在业务中的使用场景和产品价值，具体模型、算法、接口和技术实现细节放到 AI 专项需求中单独说明。

## 2. 二期核心需求

### 2.1 AI 个性化推荐

二期需要开始引入 AI 个性化推荐能力，根据用户的兴趣、历史参与记录、评价偏好、地理位置、角色身份等信息，为用户推荐更适合的行家和局。

AI 在二期主要用于提升匹配效率和内容分发质量，让玩家更快找到适合自己的服务，让行家和领路人更容易找到合适的人和局。

AI 推荐使用场景包括：

| 场景 | AI 用途 |
| --- | --- |
| 首页推荐 | 根据用户偏好推荐适合的局 |
| 行家推荐 | 给玩家推荐匹配度更高的行家 |
| 局推荐 | 根据用户兴趣、位置和历史行为推荐适合参与的局 |
| 领路人撮合 | 帮助领路人发现更适合撮合的用户和局 |
| 内容排序 | 让更符合用户需求的局优先展示 |

### 2.2 IM 接入 AI 统计

二期在一期基础 IM 的基础上，引入 AI 统计和分析能力，用于辅助平台理解局内沟通情况、用户活跃度、服务体验和潜在争议风险。

AI 统计主要用于帮助平台做运营分析和服务复盘，例如统计局内沟通活跃度、用户参与情况、服务完成情况、争议高发环节等，为后续优化组局流程、行家服务质量和平台规则提供依据。

### 2.3 高级 IM 即时通讯

一期 IM 只做文字和图片，二期需要增强局内沟通能力，加入更完整的即时通讯功能。

二期 IM 主要补充：

| 功能 | 说明 |
| --- | --- |
| 音频通话 | 支持局内成员进行语音沟通 |
| 视频通话 | 支持行家与玩家进行更直接的线上沟通 |
| 消息状态 | 展示已读、未读、发送失败等状态 |
| 消息管理 | 支持更完整的消息记录、归档和后台查看 |
| AI 统计 | 对局内沟通情况进行基础统计和辅助分析 |

### 2.4 城市探索特色玩法

二期需要在地图基础能力上增加城市探索和特色玩法，让用户不只是查找附近的局，也能围绕城市、地点、足迹形成更强的参与感。

二期增加：

| 能力 | 说明 |
| --- | --- |
| 用户足迹 | 记录用户参与过的局、去过的地点和城市轨迹 |
| 城市探索 | 按城市展示特色局、热门地点和推荐玩法 |
| 地点内容沉淀 | 将局与地点绑定，形成可持续浏览的地点内容 |
| 地图互动 | 让用户通过地图发现局、回顾足迹、查看附近机会 |

### 2.5 推荐适合的行家和局

二期需要把推荐能力从简单列表升级为更个性化的匹配推荐。

推荐对象包括：

- 给玩家推荐适合的行家。
- 给玩家推荐适合参与的局。
- 给行家推荐适合发起或参与的局。
- 给领路人推荐适合撮合的人和局。

推荐依据包括用户兴趣、历史参与、评价结果、地理位置、角色身份、局类型、服务能力等。具体 AI 推荐逻辑后续单独写入 AI 需求。

### 2.6 真实支付与分账接入

一期不接入真实支付，但必须保证支付、订单、评价、争议、结算、分账的流程设计是正确的。二期开始接入真实支付能力，并将一期设计好的流程落到真实交易链路中。

二期需要接入：

| 能力 | 说明 |
| --- | --- |

| 退款处理 | 支持异常、取消、争议后的退款流程 |
| 分账处理 | 服务完成且无争议后，按规则触发分账 |
| 对账能力 | 后台可查看支付、退款、分账和失败记录 |

二期支付与分账需要延续一期补充说明中的合规原则：资金通过正规支付通道流转，服务完成和争议处理后再按规则分账，所有资金状态都需要后台留痕。

### 2.7 手机端用户反馈优化

二期需要基于一期上线后的真实用户反馈，对手机端操作流程、页面体验和功能细节进行优化。

优化方向包括：

| 方向 | 说明 |
| --- | --- |
| 操作流程优化 | 减少不必要步骤，让报名、入局、评价更顺畅 |
| 页面体验优化 | 根据真实使用反馈调整页面布局、按钮、提示文案 |
| 反馈入口 | 在手机端增加用户反馈、问题上报或意见提交入口 |
| 数据复盘 | 结合用户反馈、访问数据和转化数据判断优先优化点 |
| 版本迭代 | 将用户反馈沉淀为二期持续优化清单 |

## 3. 二期开发方案

### 3.1 开发思路

二期按照“体验增强、真实交易、地图玩法、AI 推荐”的主线推进，确保用户体验、交易闭环和个性化推荐能力同步完善。

开发顺序：

1. 先完成手机端用户反馈优化和基础体验调整。
2. 再扩展高级 IM，加入音视频和更完整的消息状态。

4. 再补充地图足迹、城市探索和特色玩法。

| 用户反馈 | 基础评价和反馈 | 根据手机端真实反馈持续优化 |

### 3.3 二期交付重点

二期交付需要验证以下结果：

- 用户能更容易找到适合自己的行家和局。
- 局内沟通体验更完整，能支持更复杂的服务场景。
- 地图不只是定位工具，也能形成足迹和城市探索体验。
- 真实支付和分账流程可以上线运行，并能被后台追踪和对账。
- 手机端体验能根据真实用户反馈持续优化。

## 三、AI 智能推荐与 IM 智能分析方案

## 1. AI 建设目标

第三部分重点建设 AI 智能推荐与 IM 智能分析能力。目标是把平台从“用户自己找局、找行家、找资源”，升级为“系统主动理解用户、匹配局、推荐行家、辅助领路人撮合、帮助后台运营判断服务质量”。

AI 能力不是单独放在某一个页面的小功能，而是一套可以持续复用的智能基础能力。后续首页推荐、附近推荐、城市探索、行家推荐、领路人撮合、IM 服务复盘、运营风险预警、后台策略配置，都可以基于这套 AI 能力逐步扩展。

## 2. AI 智能推荐中台

### 2.1 建设内容

二期建设 AI 智能推荐中台，将平台内的玩家、行家、领路人、局、评价、IM、LBS 位置、历史行为等数据统一接入推荐系统。

推荐系统不再只按照时间、距离、分类展示内容，而是根据用户兴趣、角色身份、历史参与、服务评价、信用情况、地理位置、活跃习惯等维度，主动推荐更合适的局、行家和撮合机会。

### 2.2 推荐中台能力

| 能力 | 说明 |
| --- | --- |
| 数据接入 | 接入用户、局、行家、领路人、评价、IM、位置、行为日志等数据 |
| 画像建模 | 为用户、局、行家、领路人建立可持续更新的画像 |
| 候选召回 | 从大量局、行家和用户中筛选出可能匹配的候选对象 |
| 匹配计算 | 计算用户与局、用户与行家、领路人与局之间的匹配度 |
| 智能排序 | 结合兴趣、距离、评分、信用、热度、成局概率等因素排序 |
| 反馈学习 | 根据曝光、点击、报名、入局、评价、复玩等行为持续优化推荐 |

### 2.3 输出场景

AI 推荐中台通过接口向小程序端、领路人端和后台端输出推荐结果。

| 使用场景 | 输出内容 |
| --- | --- |
| 小程序首页 | 为用户推荐适合的局和行家 |
| 附近页面 | 推荐附近且匹配用户兴趣的局 |
| 局详情页 | 推荐相似局、相关行家和再玩一局 |
| 行家主页 | 推荐适合该行家的潜在用户和服务方向 |
| 领路人撮合端 | 推荐适合邀请的人、适合撮合的局和行家 |
| 城市探索 | 推荐城市特色局、热门地点和个性化玩法 |
| 后台运营端 | 查看推荐效果、转化数据和策略表现 |

## 3. AI 用户画像与动态标签系统

### 3.1 用户画像内容

系统为每个用户建立动态 AI 画像。用户画像不仅依赖用户手动选择的兴趣标签，还会结合注册资料、角色身份、浏览行为、报名记录、入局记录、收藏记录、评价内容、活跃时间、地理位置、会员等级、投诉申诉等数据，判断用户的兴趣偏好、消费倾向、信用情况、活跃程度和潜在需求。

### 3.2 标签示例

| 标签类型 | 示例 |
| --- | --- |
| 兴趣偏好 | 创业交流、线下社交、技能学习、高端体验、城市探索 |
| 参与偏好 | 小规模局、线下局、深度咨询局、轻体验局、复玩型用户 |
| 消费偏好 | 免费体验、低价尝试、中高客单、会员权益敏感 |
| 活跃特征 | 高频浏览、高报名率、高评价率、沉默用户、复玩用户 |
| 信用特征 | 履约稳定、评价良好、争议较少、取消较多、投诉风险 |
| 位置偏好 | 常驻城市、常参与区域、附近局偏好、跨城参与偏好 |

### 3.3 动态更新机制

用户画像会持续更新。用户每一次浏览、点击、报名、入局、评价、取消、复玩，都会影响画像权重。系统会从早期的基础推荐，逐步进入更精准的个性化推荐。

例如，一个用户多次浏览“创业交流、私董会、线下高端社交”相关的局，并且经常报名小规模线下局，系统可以逐步识别该用户具有“创业交流偏好”“高质量社交偏好”“线下局偏好”“小圈层参与型用户”等特征，后续优先推荐与这些特征匹配的局和行家。

## 4. 局画像、行家画像与领路人画像

AI 系统不仅识别用户，也需要识别平台内的局、行家和领路人。通过四类画像匹配，实现“人、局、行家、领路人”之间的智能连接。

### 4.1 局画像

局画像基于局标题、局主题、局介绍、局类型、地点、价格、人数、发起人、历史成局率、用户评价、争议情况等数据生成。

系统需要识别这个局适合什么样的人群，属于什么服务类型，偏社交还是偏服务，偏轻量体验还是深度咨询，以及适合优先推荐给哪些用户。

### 4.2 行家画像

行家画像基于技能方向、服务领域、历史成局数、平均评分、履约率、响应速度、复购率、投诉率、用户评价文本等数据生成。

系统需要判断行家更适合服务哪类用户，擅长什么类型的局，在哪些场景下转化率更高，以及后续适合获得哪些曝光机会。

### 4.3 领路人画像

领路人画像基于邀请成功率、撮合成局率、人脉质量、跟进效率、收益表现、服务满意度等数据生成。

系统可以辅助领路人判断哪些用户适合邀请，哪些局更容易成团，哪些行家适合引入当前资源圈层，从而提升撮合效率。

---

## 5. 语义匹配与智能推荐引擎

### 5.1 语义匹配能力

系统会将用户画像、局内容、行家能力、评价内容、IM 复盘摘要等文本信息转化为 AI 可计算的语义特征。相比普通关键词匹配，语义匹配可以识别更深层的需求关系。

例如，用户画像体现的是“高质量线下社交、创业交流、资源链接、私密小圈层”，某个局的描述是“创业者小范围深度交流、行家经验分享、线下闭门局”。即使两者没有完全相同的关键词，系统也能判断它们属于高度匹配的内容，从而提高推荐优先级。

### 5.2 多阶段推荐链路

推荐引擎采用多阶段链路输出结果：

| 阶段 | 说明 |
| --- | --- |
| 候选召回 | 通过兴趣标签、地理位置、历史行为、语义相似度、关系链、热门趋势等方式召回候选局或行家 |
| 业务过滤 | 过滤审核未通过、人数已满、状态异常、距离过远、信用异常、角色权限不匹配的内容 |
| 综合排序 | 根据兴趣匹配、距离、评分、信用、价格偏好、成团概率、活跃时间、运营权重等因素排序 |
| 反馈学习 | 记录曝光、点击、报名、入局、评价、复玩等行为，并反向优化推荐权重 |

不同页面可以使用不同排序策略：首页偏兴趣匹配，附近页面偏距离和成团概率，行家推荐偏服务能力匹配，领路人端偏撮合成功率。

## 6. AI 个性化推荐场景

AI 推荐覆盖玩家、行家和领路人三类角色。不同角色看到的推荐内容不同，推荐目标也不同。

### 6.1 玩家端推荐

| 推荐场景 | 说明 |
| --- | --- |
| 为你推荐的局 | 根据兴趣、位置、历史行为和评价偏好推荐适合参与的局 |
| 附近适合你的局 | 在附近局基础上叠加个性化匹配，不只是按距离排序 |
| 相似兴趣局 | 根据用户已浏览或已参与的局，推荐相似主题内容 |
| 适合你的行家 | 推荐服务能力、评价和风格更匹配的行家 |
| 再玩一局推荐 | 根据用户复玩意向和历史体验推荐下一次可参与的局 |

### 6.2 行家端推荐

| 推荐场景 | 说明 |
| --- | --- |
| 适合发起的局主题 | 根据用户需求趋势和行家能力，推荐更容易成局的主题 |
| 潜在高意向玩家 | 推荐可能对该行家服务感兴趣的用户群体 |
| 适合服务的人群 | 帮助行家理解自身更适合服务哪类用户 |
| 服务方向优化 | 根据评价和转化数据，提示行家优化服务内容和表达方式 |

### 6.3 领路人端推荐

| 推荐场景 | 说明 |
| --- | --- |
| 推荐撮合对象 | 根据用户画像和局画像，推荐适合撮合的人 |
| 推荐可邀请用户 | 从领路人人脉中识别更有可能入局的用户 |
| 推荐适合引入的行家 | 帮助领路人找到更适合当前圈层的行家 |
| 推荐即将成团的局 | 帮助领路人优先推动成团概率更高的局 |

## 7. IM AI 智能分析系统

### 7.1 建设内容

IM AI 分析模块用于对局内沟通过程进行智能统计和服务复盘。系统会将局内沟通过程转化为可量化、可追踪、可运营的服务质量数据，帮助平台了解每个局的沟通活跃度、服务完成情况、用户情绪和潜在争议风险。

### 7.2 分析维度

| 维度 | 说明 |
| --- | --- |
| 消息活跃度 | 统计消息量、发言人数、沉默用户比例 |
| 响应效率 | 统计行家响应速度、领路人跟进情况 |
| 服务进度 | 分析关键节点是否沟通清楚，服务是否推进 |
| 用户情绪 | 识别满意、不满、犹豫、投诉倾向等表达 |
| 风险倾向 | 识别退款倾向、争议倾向、投诉倾向、服务未完成风险 |
| 局后复盘 | 局结束后生成本局沟通摘要和运营建议 |

### 7.3 局后复盘摘要

局结束后，AI 可以生成一份局后复盘摘要，例如：

- 本局沟通是否活跃。
- 行家是否及时响应。
- 领路人是否完成跟进。
- 用户是否出现不满表达。
- 是否存在退款或投诉倾向。
- 服务是否基本完成。
- 是否需要运营介入。

后台运营人员优先看到结构化结果和风险标签，而不是直接查看大量原始聊天记录。这样可以提升运营效率，也能减少对用户隐私的无序暴露。

## 8. IM 风险预警与运营复盘

二期在 IM 基础能力上增加风险识别和运营预警机制。系统会识别局内沟通中的异常情况，例如用户不满、服务争议、退款倾向、投诉倾向、行家长时间未响应、领路人未跟进、群内异常沉默等，并在后台形成风险提示。

### 8.1 风险评分

| 评分 | 说明 |
| --- | --- |
| 活跃度评分 | 判断局内成员是否充分沟通 |
| 响应效率评分 | 判断行家和领路人是否及时响应 |
| 情绪风险评分 | 判断用户是否出现负向情绪 |
| 服务完成度评分 | 判断本局服务是否按流程推进 |
| 争议风险等级 | 判断是否需要运营提前介入 |

### 8.2 后台预警看板

后台可以展示高风险局、低活跃局、争议高发局、响应较慢行家、撮合效率较低领路人等数据。运营人员可以根据系统预警提前介入，降低申诉成本，提高服务体验稳定性。

---

## 9. 关系链与领路人撮合推荐

平台具备邀请制和永久关系绑定的业务基础，二期可进一步建设关系链推荐能力。系统会基于邀请关系、历史组局、共同参与、评价互动、领路人撮合记录、行家服务记录等数据，构建人与人、人与局、人与行家之间的关系网络。

### 9.1 关系链数据

| 数据 | 说明 |
| --- | --- |
| 邀请关系 | 谁邀请了谁，邀请链路如何形成 |
| 组局关系 | 谁和谁共同参与过局 |
| 评价关系 | 谁评价了谁，评价结果如何 |
| 撮合关系 | 哪个领路人撮合了哪些人和局 |
| 服务关系 | 哪些用户接受过哪些行家的服务 |
| 复玩关系 | 哪些用户愿意继续参与相似局 |

### 9.2 撮合推荐

系统可以计算用户之间的关系强度、领路人的人脉质量、某个用户适合被谁邀请、某个行家适合进入哪个圈层。

例如，某个领路人过去多次成功撮合创业类、高端社交类局，系统可以优先向他推荐这类局和相关用户；某个玩家经常参与某类行家的服务，系统可以向领路人提示该玩家具备较高转化概率。

## 10. 后台 AI 推荐配置与效果追踪

后台需要提供 AI 推荐配置和效果追踪能力。平台运营人员可以根据业务目标调整推荐策略，例如优先推荐高评分行家、优先推荐即将成团的局、优先推荐附近局、提高高信用用户创建局的曝光权重、降低争议率较高内容的推荐优先级等。

### 10.1 后台配置能力

| 能力 | 说明 |
| --- | --- |
| 推荐策略配置 | 配置不同页面和角色的推荐目标 |
| 权重调节 | 调整兴趣、距离、评分、成团概率、运营策略等权重 |
| 推荐日志 | 记录每次推荐曝光、点击、报名、入局等数据 |
| 转化看板 | 展示首页推荐、附近推荐、行家推荐、领路人推荐的转化效果 |
| A/B 测试 | 对比不同推荐策略的效果，持续优化推荐结果 |

### 10.2 效果指标

| 指标 | 说明 |
| --- | --- |
| 推荐曝光量 | 推荐内容被用户看到的次数 |
| 点击率 | 用户点击推荐内容的比例 |
| 报名率 | 用户看到推荐后报名或申请入局的比例 |
| 成局率 | 推荐带来的成功成团比例 |
| 评价得分 | 推荐带来的服务体验质量 |
| 复玩率 | 用户再次参与相似局的比例 |
| 撮合成功率 | 领路人通过推荐完成撮合的比例 |

这样可以让 AI 推荐既具备自动分发能力，也保留平台运营控制权。

## 11. 数据安全与权限控制

AI 推荐和 IM 分析会涉及用户行为、评价、位置、聊天摘要等敏感数据，因此需要配套数据安全和权限控制机制。

### 11.1 权限原则

| 原则 | 说明 |
| --- | --- |
| 分级查看 | 不同后台角色只能查看与职责相关的数据 |
| 摘要优先 | 后台优先展示统计指标、风险标签和 AI 摘要 |
| 原文受控 | 只有投诉、申诉、争议处理等必要场景下，授权管理员才能查看原始记录 |
| 数据脱敏 | 展示用户信息、聊天摘要、评价内容时进行必要脱敏 |
| 操作留痕 | 所有查看、导出、处理操作都记录操作日志 |

### 11.2 展示方式

IM 分析结果可以采用摘要化和脱敏化方式展示，例如展示“存在退款倾向”“行家响应较慢”“用户负面情绪较高”，而不是直接将全部聊天内容暴露给后台人员。这样可以兼顾平台运营、争议处理和用户隐私保护。

## 12. 整体架构

二期 AI 系统采用“AI 推荐中台”架构，将小程序端、后台管理端和后端业务系统产生的数据统一接入 AI 数据层。数据经过清洗、打标、画像建模、语义处理和智能排序后，通过推荐接口输出到各业务场景。

| 架构层 | 说明 |
| --- | --- |
| 数据层 | 接入用户、角色、局、订单、评价、IM、LBS、分润、行为日志等基础数据 |
| 画像层 | 生成用户画像、局画像、行家画像、领路人画像，并持续更新标签和特征权重 |
| AI 引擎层 | 负责语义理解、画像匹配、IM 摘要、情绪识别、风险识别和推荐分数计算 |
| 推荐服务层 | 向小程序端和后台端提供首页推荐、附近推荐、行家推荐、领路人撮合推荐、相似局推荐等接口 |
| 运营分析层 | 展示推荐效果、IM 分析结果、风险预警、服务复盘和后台策略配置 |

该架构具备扩展性，后续可以继续支持城市探索、SaaS 商家接入、商家推荐、平台级运营推荐等能力。

---

## 13. 方案价值

二期 AI 能力的核心价值，是将平台从“用户主动找局”升级为“系统主动匹配人、局、行家和领路人”。

| 价值 | 说明 |
| --- | --- |
| 提升玩家找局效率 | 用户更容易发现符合自己兴趣、位置和需求的局 |
| 提升行家服务转化 | 行家更容易触达适合自己的用户和服务场景 |
| 提升领路人撮合成功率 | 领路人可以获得更清晰的撮合对象和局推荐 |
| 提升平台运营效率 | 后台可以看到推荐效果、服务质量和风险预警 |
| 沉淀数据资产 | 用户行为、评价、IM、LBS、关系链逐步沉淀为可持续优化的数据基础 |
| 增强用户粘性 | 个性化推荐、城市探索和再玩一局能力提升用户持续参与意愿 |
